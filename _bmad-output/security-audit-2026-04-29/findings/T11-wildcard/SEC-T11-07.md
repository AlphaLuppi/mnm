## Description

Three distinct production-bypasses are gated solely on `MNM_E2E_SEED === "true"`:

**1. Rate limiter completely disabled** (`rate-limit.ts:118`):
```typescript
const isE2eMode = process.env.MNM_E2E_SEED === "true";
return async (req, res, next) => {
  if (isE2eMode) { next(); return; }  // ALL rate limits bypassed
```

**2. BetterAuth rate limiting disabled** (`better-auth.ts:241`):
```typescript
...(isE2eMode ? { rateLimit: { enabled: false } } : {})
```
This disables the auth layer's own brute-force protection on login endpoints.

**3. E2E seed routes exposed** (`e2e-seed.ts`): These routes allow:
- `POST /api/e2e-seed/ensure-access` → grants `instance_admin` role + company membership to any authenticated user
- `POST /api/e2e-seed/cleanup` → deletes test data (destructive)

The protection is only:
```typescript
function isE2eEnabled(): boolean {
  return process.env.MNM_E2E_SEED === "true";
}
```

There is no second factor, no IP restriction, no separate secret. If this env var is set by accident in production (e.g., in a CI/CD pipeline that copies all test env vars), any authenticated user can grant themselves `instance_admin`.

The risk is compounded by Docker Compose configurations — `docker-compose.test.yml` sets `MNM_E2E_SEED=true` and if that file is accidentally used for production deployment, all three bypasses are active.

## Impact

- **Rate limiting bypass**: Enables brute-force attacks on login, API endpoints without throttling.
- **Admin escalation**: Any authenticated user can call `POST /api/e2e-seed/ensure-access` to get instance_admin.
- **Data destruction**: `POST /api/e2e-seed/cleanup` can delete companies, agents, traces in bulk.

## Reproduction (creative PoC)

```bash
# If MNM_E2E_SEED=true is set in production:
# 1. Login with any valid account
# 2. Escalate to instance admin
curl -X POST https://mnm.prod/api/e2e-seed/ensure-access \
  -H "Cookie: better-auth.session_token=..." \
  -H "Content-Type: application/json"
# Response: {"success": true, ...} + caller now has instance_admin

# 3. Create any company and own the platform
```

## Recommendation

1. **Rename env var**: Use `MNM_TEST_E2E_SEED` and ensure it is explicitly excluded from all production deployment templates.
2. **Add secondary secret**: Require an additional `MNM_E2E_SECRET` header/token for e2e-seed routes, not just the env var.
3. **Runtime guard**: At startup, if `NODE_ENV=production` and `MNM_E2E_SEED=true`, log a `CRITICAL` warning and refuse to start.
4. **Add to .env.example**: Document that `MNM_E2E_SEED` must NEVER be set in production.
