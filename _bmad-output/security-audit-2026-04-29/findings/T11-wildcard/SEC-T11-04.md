## Description

When a webhook routine trigger is created, a 32-byte random secret is generated and stored **as-is** (plaintext hex string) in the `secret_hash` column:

```typescript
// routines.ts ~line 727-729
values.publicId = crypto.randomBytes(16).toString("hex");
const secret = crypto.randomBytes(32).toString("hex");
values.secretHash = secret; // stored as hex; verified via HMAC or bearer comparison
```

Despite the column name `secret_hash`, no hashing is applied. The comment literally says "stored as hex; verified via HMAC or bearer comparison."

Verification later reads the raw plaintext:
```typescript
const secret = trigger.secretHash!;  // plaintext hex
// used directly in: timingSafeCompare(token, secret)  or createHmac("sha256", secret)
```

This means:
- A SQL injection, DB backup exposure, or insider threat **immediately** exposes every webhook secret for every tenant.
- The "hash" naming is misleading — developers reviewing DB contents may not realize it's plaintext.

Note: the secret is returned once to the caller at creation time ("only shown once at creation") which is a correct pattern, but the server-side storage should use a KDF (bcrypt, argon2, scrypt) or at minimum a HMAC with a server-side key (similar to how BetterAuth handles session tokens).

## Impact

- A DB read (e.g., via sqli, backup leak, cloud misconfiguration) exposes **all webhook secrets for all tenants**.
- Attacker can replay webhooks or forge HMAC signatures for any routine.
- Combined with `replayWindowSec` defaulting to **300 seconds** (5 minutes), an attacker with DB access has a 5-minute window to forge and replay any webhook.

## Reproduction (creative PoC)

```sql
-- Attacker has DB read access
SELECT public_id, secret_hash FROM routine_triggers WHERE signing_mode = 'bearer';
-- All secrets are directly usable as bearer tokens or HMAC keys
```

## Recommendation

Two options:

**Option A (preferred — KDF at storage)**: Hash the secret before storing using `bcrypt` or `scrypt`. Verify via bcrypt.compare(). Note: this means HMAC-based signing mode (`hmac_sha256`) cannot be used with hashed storage — it requires the plaintext secret as the HMAC key. For HMAC mode, use Option B.

**Option B (server-side envelope encryption)**: Encrypt secrets using the existing `MNM_SECRETS_MASTER_KEY` / local-encrypted-provider before storing. This provides at-rest protection without breaking HMAC verification.

**Minimum viable fix**: Use `crypto.createHmac("sha256", SERVER_SIGNING_KEY).update(secret).digest("hex")` as the stored value for bearer mode, and store the encryption-wrapped secret for HMAC mode.

Also consider reducing `replayWindowSec` default from 300s to 30s.
