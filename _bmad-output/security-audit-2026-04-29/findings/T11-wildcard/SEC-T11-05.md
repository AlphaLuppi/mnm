## Description

The board-claim challenge (`board-claim.ts`) uses a module-level singleton `activeChallenge` and a two-step pattern:

1. `getChallengeStatus()` checks `activeChallenge.claimedAt === null` (line 38)
2. `claimBoardOwnership()` calls `getChallengeStatus()` again, then runs a DB transaction, then **sets** `activeChallenge.claimedAt = new Date()` **after** the transaction (line 133)

```typescript
// board-claim.ts ~line 89-135
export async function claimBoardOwnership(...) {
  const status = getChallengeStatus(opts.token, opts.code);   // T1: check
  if (status !== "available") return { status };

  await db.transaction(async (tx) => {                        // DB writes (slow)
    // ... grants instance_admin to userId ...
    // ... adds company memberships ...
  });

  if (activeChallenge && activeChallenge.token === opts.token) {
    activeChallenge.claimedAt = new Date();                  // T2: mark used (AFTER tx)
    activeChallenge.claimedByUserId = opts.userId;
  }
  return { status: "claimed", claimedByUserId: opts.userId };
}
```

Between T1 (check) and T2 (mark used), two concurrent POST requests can both pass the `getChallengeStatus()` check, both complete the DB transaction, and both gain `instance_admin`. The in-memory singleton has no mutex.

This is only exploitable in `authenticated` mode where a board-claim challenge is active (i.e., on first setup with no real admin yet), but that is exactly when the attack surface is most sensitive — a race during the bootstrapping claim could allow two different users to both become instance admins simultaneously, both believing they are the sole admin.

Additionally: `getChallengeStatus()` compares `activeChallenge.token !== token` and `activeChallenge.code !== (code ?? "")` using plain string comparison (`!==`). JavaScript `!==` on strings is NOT constant-time (V8 short-circuits at first differing character). For the token (48 hex chars from `randomBytes(24)`), this is a timing oracle — although the entropy (192 bits) is high enough that a timing attack is impractical in practice.

## Impact

- **Race condition**: Two users posting simultaneously during first-boot setup can both become instance admins.
- **Single-use guarantee broken**: The challenge token is supposed to be single-use ("one-time bootstrap"), but concurrent requests can claim it twice.
- **Low practical risk** in normal single-user setup scenarios, but a concern for automated deployment pipelines where multiple processes might attempt to claim simultaneously.

## Reproduction (creative PoC)

```python
import asyncio, aiohttp

# Two concurrent POST requests with the same token+code
async def claim(session, url, code, user_token):
    async with session.post(url, json={"code": code},
                            headers={"Authorization": f"Bearer {user_token}"}) as r:
        return await r.json()

async def race():
    url = "http://mnm.local/api/board-claim/{token}/claim"
    async with aiohttp.ClientSession() as s:
        results = await asyncio.gather(
            claim(s, url, "{code}", "userA_session"),
            claim(s, url, "{code}", "userB_session"),
        )
    print(results)  # Both may return {"claimed": true, "userId": ...}

asyncio.run(race())
```

## Recommendation

1. **Atomic lock before DB write**: Set `activeChallenge.claimedAt = new Date()` BEFORE the DB transaction (optimistic lock). If the challenge is already marked claimed, reject early.

```typescript
// Atomic in-memory claim before DB write
if (activeChallenge.claimedAt !== null) return { status: "claimed" };
activeChallenge.claimedAt = new Date();  // mark immediately, BEFORE async IO
activeChallenge.claimedByUserId = opts.userId;

await db.transaction(async (tx) => { /* ... */ });
```

2. Use `crypto.timingSafeEqual` for token/code comparison (defense in depth even though entropy is sufficient).
