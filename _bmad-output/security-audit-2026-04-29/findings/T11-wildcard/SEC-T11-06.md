## Description

The `requirePermission` middleware for agent actors has this fallback logic:

```typescript
// require-permission.ts ~line 70-81
if (req.actor.type === "agent") {
  let allowed = await access.hasPermission(companyId, "agent", agentId, permissionKey);
  if (!allowed && req.actor.creatorUserId) {
    allowed = await access.canUser(companyId, req.actor.creatorUserId, permissionKey);
  }
  // ...
}
```

`access.canUser` checks the creator's CURRENT role and permissions. However, `resolveRole` uses a **5-minute in-memory cache** (`roleCache`):

```typescript
// access.ts: CACHE_TTL_MS = 5 * 60 * 1000
const cached = roleCache.get(key);
if (cached && !isStale(cached.cachedAt)) return cached;
```

Scenario:
1. User Alice (high-privilege) creates an agent.
2. An admin demotes Alice or suspends her membership.
3. For up to 5 minutes, the agent still inherits Alice's old permissions from the cache.
4. During those 5 minutes, Alice's agent can still perform privileged operations.

Additionally: if Alice is **suspended** (`status: "suspended"`), `resolveRole` returns `null` because it checks `membership.status !== "active"`. BUT `canUser` → `hasPermission` calls `resolveRole`, which would return null, returning false — so suspension is handled correctly for the role path. However, agents that have **direct `agent_permissions` rows** are checked BEFORE the creator fallback:

```typescript
// access.ts ~line 208-217 (hasPermission)
// For agents: also check direct permissionSlugs stored on the agent record
if (principalType === "agent") {
  const agentRow = await db.select({ permissions: agents.permissions })...
  const normalized = normalizeAgentPermissions(agentRow.permissions);
  if (normalized.permissionSlugs.includes(permissionKey)) return true;
}
```

Direct `agent_permissions` rows are checked with NO cache invalidation path tied to the creator's status. If an agent has direct permissions seeded at creation time (e.g., via `permissionSlugs` during hire), those permissions persist even after the creator is suspended — and `invalidateRoleCache` does NOT clear agent_permissions rows.

## Impact

- 5-minute window where suspended/demoted creators' agents retain elevated permissions.
- Agents with directly-granted permissions retain them permanently regardless of creator status.
- In a "hire and fire" scenario (user leaves, their agents should lose rights), the agent continues operating with stale permissions.

## Reproduction

```
T=0: Admin grants Alice high-privilege role. Alice creates agent A with direct agent_permissions.
T=1: Admin suspends Alice (membership.status = 'suspended'), removes her role.
T=2: Agent A calls requirePermission → checks direct agent_permissions → allowed = true
     (creator fallback never needed because direct permissions match first)
T=∞: Agent A retains permissions indefinitely.
```

## Recommendation

1. When a user is suspended or has their role changed, also cascade to their created agents:
   - Either terminate/pause those agents automatically, OR
   - Strip their direct `agent_permissions` rows, OR  
   - Tie agent permission resolution to creator active status as a prerequisite check.

2. Add `agent_permissions`-level cache invalidation when creator membership changes.

3. Reduce the role cache TTL from 5 minutes to 30-60 seconds for sensitive deployments.
