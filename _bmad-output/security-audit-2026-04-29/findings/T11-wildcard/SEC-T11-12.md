## Description

Advisory locks use `hashtext()` (PostgreSQL's CRC32-based text hash) to derive a 32-bit integer lock key:

```typescript
// governed-workflows.ts ~line 571
sql`SELECT pg_advisory_xact_lock(hashtext(${"mnm:launch:" + def.id}))`

// config-layer-conflict.ts ~line 103
sql`SELECT pg_advisory_xact_lock(hashtext('agent_config_' || ${agentId}))`
```

`hashtext()` returns a 32-bit signed integer. The birthday probability of a collision among N distinct lock strings is approximately `N²/2^32`. With thousands of workflow definitions across many tenants, the probability of two distinct `def.id` values hashing to the same advisory lock key is non-negligible.

A hash collision between two unrelated workflows (from different tenants!) causes:
1. **False serialization**: Two concurrent launches of entirely different workflows are serialized behind the same advisory lock, causing one to wait unnecessarily. In a high-load multi-tenant system, this could cause DoS-like slowdowns for specific workflows.
2. **Cross-tenant information leak**: The timing of lock acquisition reveals to one tenant that another tenant's workflow is currently launching (timing side channel).

The lock key space is 32 bits (2^32 ≈ 4 billion values). With 1000 workflows: collision prob ≈ 0.01%. With 100,000 workflows: ≈ 1%.

Note: This does NOT cause correctness issues (the lock correctly serializes access to the hashed key; colliding workflows just experience unnecessary serialization), but it is a latency side channel.

## Impact

- **Low**: Correctness is preserved; only latency is affected.
- **Cross-tenant information leak**: Lock acquisition latency reveals when another tenant's workflow is active (timing oracle, difficult to exploit in practice).
- **DoS amplification**: In pathological cases, many workflows hashing to the same key create a serialization bottleneck.

## Reproduction

```python
# Find two workflow definition IDs that hash to the same pg hashtext value
# Use PostgreSQL hashtext() to brute-force collisions:
import struct, ctypes
def hashtext(s):
    # Approximate CRC32-based implementation
    return ctypes.c_int32(sum(ord(c) for c in s)).value  # simplified

# With enough workflow IDs, collisions are inevitable
```

## Recommendation

1. Use `pg_advisory_xact_lock(bigint)` with a 64-bit hash (e.g., `hashtext64` or `('x' || md5(str))::bit(64)::bigint`) to dramatically reduce collision probability.
2. Alternative: use a dedicated PostgreSQL sequence or application-level mutex table instead of advisory locks.

```sql
-- Better approach: 64-bit hash
SELECT pg_advisory_xact_lock(('x' || md5($1))::bit(64)::bigint)
```
