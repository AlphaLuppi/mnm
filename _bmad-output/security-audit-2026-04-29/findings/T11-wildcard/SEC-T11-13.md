## Description

The AI assistant concurrency limiter uses `companyId:userId` as the key, but for agents (which don't get a `userId`) it falls back to `"anon"`:

```typescript
// governed-workflows-ai.ts ~line 87-94
const userId = req.actor?.type === "board" ? req.actor.userId ?? null : null;
const limitKey = `${companyId}:${userId ?? "anon"}`;
if (!concurrency.acquire(limitKey)) {
  return apiError(res, 429, "AI_RATE_LIMIT", "Too many concurrent AI assistant requests for this user", ...);
}
```

The endpoint requires `WORKFLOWS_CREATE` permission, so agents CAN access it. When multiple agents from the same company call the AI assistant concurrently, they all share the `{companyId}:anon` bucket (max 3 concurrent). This means:
1. 3 agents simultaneously using the AI assistant → 4th agent gets rate-limited even if it has never used the assistant.
2. A single misbehaving agent can DoS other agents' AI assistant access within the same company.

This is a minor resource exhaustion / fairness issue, not a security vulnerability, but worth noting for multi-agent deployments.

Additionally: the `concurrencyCounter` is an **in-memory Map per factory instance**. If multiple Node.js processes serve the same API (load-balanced), each process has its own counter. A client can bypass the limit by spreading requests across instances (e.g., 3 × N processes = N×3 concurrent requests).

## Impact

- Low: agent workloads are DoS'd by other agents' AI usage in the same company.
- Rate limit bypass via multiple server instances (if horizontally scaled).

## Recommendation

1. For agents, use `companyId:agentId` as the rate limit key.
2. For horizontal scaling: move the concurrency counter to Redis (shared state).
3. Consider per-company limits at a higher ceiling rather than per-user limits.
