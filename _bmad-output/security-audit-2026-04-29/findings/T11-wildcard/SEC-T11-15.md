## Description

The read endpoints for tag assignments have no `requirePermission` check — only `assertCompanyAccess`:

```typescript
// tags.ts ~line 232
router.get("/companies/:companyId/agents/:agentId/tags", async (req, res) => {
  const companyId = req.params.companyId as string;
  const agentId = req.params.agentId as string;
  // NO requirePermission or assertCompanyAccess call!
  // Falls through directly to DB query
```

And for users:
```typescript
// tags.ts ~line 201
router.get("/companies/:companyId/users/:userId/tags", async (req, res) => {
  assertCompanyAccess(req, companyId);
  // No tag-scope filter applied either
  // Returns ALL tags for the user/agent, regardless of whether the requester can see them
```

The agents endpoint doesn't even call `assertCompanyAccess`. Any authenticated actor (from any company) can enumerate the tags of any agent by ID if they can guess/know the agent UUID.

For users, `assertCompanyAccess` is called, but there is no check that the requesting user can actually see the target user. A user in company A could enumerate the tags of any user in company A, even users from completely different tag groups.

This enables **tag enumeration** — by knowing the tag UUIDs associated with users/agents, an attacker can infer the organizational structure (teams, roles, groups) of the company.

## Impact

- Low: tag names and IDs are exposed to any authenticated company member.
- Cross-user tag enumeration leaks organizational structure.
- The agents endpoint could potentially be called cross-company (no `assertCompanyAccess`) — however, the DB query includes `companyId` filter, so cross-company enumeration returns empty results.

## Recommendation

1. Add `assertCompanyAccess(req, companyId)` to the agent tags GET endpoint.
2. Consider adding `requirePermission(db, PERMISSIONS.TAGS_READ)` to both read endpoints for consistency.
3. For user tag endpoints, verify the requesting user can see the target user (share at least one tag or is admin).
