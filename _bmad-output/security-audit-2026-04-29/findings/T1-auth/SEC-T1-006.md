## Description

Agent permission checks implement a fallback: if the agent itself does not have a required permission, the system checks whether the agent's creator has that permission and, if so, grants the action:

```typescript
// require-permission.ts:106–109
let allowed = await access.hasPermission(companyId, "agent", agentId, permissionKey);
if (!allowed && req.actor.creatorUserId) {
  allowed = await access.canUser(companyId, req.actor.creatorUserId, permissionKey);
}
```

This pattern means **a compromised agent token acts with effectively the same permissions as the user who created it** — the agent can perform any action that the creator can perform, regardless of what permissions the agent was explicitly granted.

The `creatorUserId` is sourced from:
1. The DB record `agents.createdByUserId` (for API key auth) at `middleware/auth.ts:120, 149`.
2. The JWT claim `created_by` (for JWT auth) at `agent-auth-jwt.ts:154`, which originates from `mcp-token-verifier.ts:133`.

For JWT-authenticated agents, the `created_by` claim is **embedded in the token** and signed with the shared HMAC-HS256 secret. Any agent that can observe its own JWT (e.g., via environment variable inspection or logs) can extract the `created_by` value — but this is fixed at token creation time.

More importantly: the inheritance is unconditional. An agent assigned to a low-privilege role (e.g., read-only) will nonetheless be granted write or admin permissions if its creator has those permissions. There is no scope-down mechanism to cap agent permissions below the creator's level.

## Impact

- An agent token theft allows the attacker to operate with the creator user's full permission set, not the agent's restricted set.
- Agents that are supposed to be scoped (e.g., "agent may only read issues") silently operate at creator level for all other permissions.
- A malicious `created_by` claim in a forged JWT (if secret is compromised per SEC-T1-001) could point to an admin user, granting full admin access.

## Reproduction

1. Create an agent assigned to a read-only role.
2. The agent's `createdByUserId` is a user with `USERS_MANAGE` permission.
3. Use the agent's JWT to call `POST /companies/:id/members/:userId/reset-password` — this requires `USERS_MANAGE`.
4. Observe the request succeeds because the creator has the permission, even though the agent's role does not.

## Recommendation

- Implement a cap: agent effective permissions = `min(agent_permissions, creator_permissions)`. The current code already computes the union; change the fallback to be an intersection only when the agent's role explicitly includes `inherits_from_creator: true`.
- Alternatively, remove the inheritance entirely and require agents to be explicitly assigned all needed permissions at creation time.
- For JWT-authenticated agents, validate that `created_by` matches `agents.createdByUserId` in the database (prevents a forged claim from pointing to a different creator).
