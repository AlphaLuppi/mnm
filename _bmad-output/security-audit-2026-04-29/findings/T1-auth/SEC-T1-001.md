## Description

Three independent token-signing systems each fall back to a well-known hard-coded secret when the corresponding environment variable is absent:

| System | File | Secret | Env var |
|--------|------|--------|---------|
| BetterAuth session | `better-auth.ts:180` | `"mnm-dev-secret"` | `BETTER_AUTH_SECRET` |
| Agent JWT | `agent-auth-jwt.ts:34` | `"mnm-dev-secret"` | `MNM_AGENT_JWT_SECRET` |
| MCP OAuth JWT | `mcp-auth-config.ts:7` | `"mnm-mcp-dev-secret"` | `MNM_MCP_JWT_SECRET` |

The guard for the BetterAuth fallback reads from `process.env` at call time (`createBetterAuthInstance`) rather than at startup, meaning a misconfigured but otherwise live production instance will silently accept the well-known secret.

Most critically: `better-auth.ts:180` checks `process.env.BETTER_AUTH_SECRET ?? process.env.MNM_AGENT_JWT_SECRET ?? "mnm-dev-secret"` **with no guard on `deploymentMode`**. If an operator forgets both env vars and deploys in `authenticated` mode, the server starts successfully (no throw) and signs session tokens with `"mnm-dev-secret"`. An attacker who knows this public secret can forge valid BetterAuth session cookies.

Compare with the agent JWT path (`agent-auth-jwt.ts:36–39`): it does throw when `deploymentMode !== "local_trusted"` and the secret is absent. BetterAuth does not have this guard.

## Impact

If `BETTER_AUTH_SECRET` and `MNM_AGENT_JWT_SECRET` are both absent in a production deployment:
- Any attacker can craft a valid BetterAuth session cookie for any user ID.
- The session passes `resolveBetterAuthSession` → actor type is `"board"` with `source: "session"` and full `isInstanceAdmin` potential.
- Complete tenant compromise of every company on the instance.

## Reproduction

1. Start server in `authenticated` mode with neither `BETTER_AUTH_SECRET` nor `MNM_AGENT_JWT_SECRET` set.
2. Confirm the server starts without error (no throw in `createBetterAuthInstance`).
3. Sign a BetterAuth session token with secret `"mnm-dev-secret"` using the BetterAuth library.
4. Send a request with the forged cookie — the session resolves to a real userId.

## Recommendation

In `createBetterAuthInstance` (or its caller in `index.ts`), throw an error when `deploymentMode === "authenticated"` and the resolved secret equals the hard-coded default. The guard already exists for the agent JWT path — replicate it here:

```typescript
// index.ts already validates at startup for agent JWT — do same for BetterAuth
const betterAuthSecret = process.env.BETTER_AUTH_SECRET?.trim() ?? process.env.MNM_AGENT_JWT_SECRET?.trim();
if (!betterAuthSecret && config.deploymentMode === "authenticated") {
  throw new Error("BETTER_AUTH_SECRET is required in authenticated mode");
}
```

The `index.ts:558` already does this check, but `better-auth.ts:180` bypasses it by having its own fallback. Remove the fallback from `createBetterAuthInstance` entirely — rely on the startup guard in `index.ts`.
