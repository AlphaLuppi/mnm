## Description

BetterAuth is configured with `requireEmailVerification: false`:

```typescript
emailAndPassword: {
  enabled: true,
  requireEmailVerification: false,
  disableSignUp: config.authDisableSignUp,
},
```

This means users can sign up with any email address and immediately access the full application without proving ownership of that email. Combined with the fact that `authDisableSignUp` defaults to `false`, the registration is completely open in a fresh deployment.

**Specific risks:**
1. **Email squatting**: An attacker signs up with `admin@company.com` before the real admin. If no instance_admin exists yet, the attacker becomes the first user and auto-promoted to `instance_admin` (via the `databaseHooks.user.create.after` hook in `better-auth.ts:247`).
2. **SSO bypass**: The `provisionOrLinkUser` function in `sso-auth.ts:326` checks for an existing user by email. If an attacker pre-registers with the victim's SSO email (`email.trim().toLowerCase()`), the SSO flow at line 329 finds the existing user and links the SSO account to the attacker's pre-registered account instead of provisioning a new one.
3. **Notification abuse**: Password reset and invitation emails sent to unverified addresses could be intercepted.

The instance_admin squatting risk (point 1) is partially mitigated because the board-claim challenge also needs to be completed, but the email squatting combined with SSO linking (point 2) is a real vector.

## Impact

- First-signup race condition with email squatting becomes instance_admin.
- Email-based SSO linking can link to an attacker's pre-registered account.
- Account enumeration: sign-up attempts reveal if an email is taken (409 Conflict).

## Recommendation

- Enable `requireEmailVerification: true` in production (`authenticated` mode).
- Gate the `instance_admin` auto-promotion in `databaseHooks` on `emailVerified: true`.
- In `provisionOrLinkUser`, require the existing account to have `emailVerified: true` before linking an SSO identity to it.
