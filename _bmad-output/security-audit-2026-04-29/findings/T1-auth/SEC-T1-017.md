## Description

Two security-critical in-memory stores are not distributed:

**1. OAuth CSRF token store** (`mcp-oauth-router.ts:154`):
```typescript
const csrfTokens = new Map<string, CsrfEntry>();
```

**2. SSO state store** (`sso-auth.ts:23`):
```typescript
const ssoStateStore = new Map<string, { companyId: string; provider: SsoProvider; createdAt: number }>();
```

In a horizontally-scaled deployment (multiple Node.js processes or containers behind a load balancer), a user who initiates an OAuth flow on instance A and is redirected back to instance B will fail because the token/state was stored only on instance A.

More importantly from a security perspective: a restart of the process clears these stores. An attacker who can observe a valid CSRF token or relay state (from logs, timing, etc.) and cause a process restart (e.g., via an unhandled exception) effectively gets a clean slate with no stored tokens to validate against — but existing tokens can no longer be validated as used. This is a minor replay risk.

The OAuth authorization code store (`OAuthStore.codes`) has the same in-memory issue — authorization codes are lost on restart, but since codes have a 60-second TTL, this is less critical.

The comment in `sso-auth.ts:21–22` explicitly acknowledges this: "In production, this should use Redis."

## Impact

- Multi-instance deployments break SSO and MCP OAuth flows.
- Process restarts within the relay state or CSRF token TTL window could allow replay in edge cases.
- Authorization codes issued but not yet exchanged are lost on restart, causing valid users to see `invalid_grant` errors.

## Recommendation

- Migrate the SSO state store and CSRF token store to Redis (already available in the infrastructure per `config.redisUrl`).
- The rate limiter already has a Redis implementation — the same pattern can be applied to these stores.
- Ensure the Redis connection uses TLS in production.
