## Description

The SSO session cookie is set with `secure: req.secure`:

```typescript
res.cookie("better-auth.session_token", session.token, {
  httpOnly: true,
  secure: req.secure,
  sameSite: "lax",
  expires: session.expiresAt,
  path: "/",
});
```

`req.secure` is Express's property that returns `true` when the protocol is HTTPS. However, in common production deployments behind a TLS-terminating reverse proxy (nginx, Traefik, Caddy), the proxy handles TLS and forwards requests to the Node.js server over HTTP. In this configuration, `req.secure` is `false` unless Express's `trust proxy` setting is enabled.

If `trust proxy` is not set (there is no evidence of `app.set("trust proxy", ...)` in `app.ts`), `req.secure` will be `false` for all requests behind a reverse proxy, and the `Secure` flag will not be set on the SSO session cookie.

A `Secure`-less session cookie can be stolen by a man-in-the-middle or sent over HTTP by the browser (if the site has any HTTP endpoints).

The BetterAuth instance has a similar concern — it checks `isHttpOnly` based on `publicUrl.startsWith("http://")` and sets `useSecureCookies: false` only explicitly for HTTP deployments. But the SSO custom cookie does not use this logic.

## Impact

- In HTTP proxied deployments without `trust proxy`, the SSO session cookie is set without the `Secure` flag.
- If the user visits any HTTP version of the site (including HTTP redirects), the browser sends the session cookie over HTTP.
- Session token exposure to network interception.

## Recommendation

- Either set `app.set("trust proxy", 1)` (trusting the first proxy hop) so `req.secure` is derived from `X-Forwarded-Proto`, or
- Hardcode `secure: process.env.NODE_ENV === "production"` for the SSO cookie, or
- Derive the `secure` flag from `config.authPublicBaseUrl.startsWith("https://")` matching the BetterAuth logic.
