## Description

The SAML callback handler (`handleSamlCallback`) performs no real cryptographic signature verification. The check at lines 132–138 reads:

```typescript
if (config.certificate) {
  // Check that the response references the certificate
  // In production, use a full XML signature validator (e.g., xml-crypto)
  const hasCertRef = decodedResponse.includes("Signature") || decodedResponse.includes("SignatureValue");
  if (!hasCertRef && !decodedResponse.includes("saml:Assertion")) {
    throw unauthorized("SAML assertion signature validation failed");
  }
}
```

This check only looks for the string `"Signature"` or `"SignatureValue"` anywhere in the XML blob. An attacker can:
1. Craft a completely forged SAML `<Response>` containing an arbitrary email/NameID.
2. Add `<Signature>Forged</Signature>` anywhere in the XML body (even in a comment or free-text element).
3. POST it to `/api/sso/saml/:companyId/acs` with a valid `RelayState` obtained by first visiting the SAML login initiation endpoint.

The relay state is single-use and verified, but obtaining one requires only a GET to `/api/sso/saml/:companyId/login` — a public, unauthenticated endpoint.

No actual certificate-based XML signature verification is performed. The `config.certificate` field is never cryptographically used.

Additionally, if `config.certificate` is null/empty (unverified or freshly synced config), the block is skipped entirely and any unsigned response is accepted.

## Impact

- Complete account takeover: forge a SAML assertion claiming any existing user's email to assume their identity.
- User impersonation and SSO-based privilege escalation to any company.
- New user auto-provisioning: claim any email address as a brand-new user (bypasses sign-up controls).

## Reproduction

1. Identify a company with SAML SSO configured.
2. GET `/api/sso/saml/:companyId/login` to obtain a valid `RelayState`.
3. Craft a forged SAML `<Response>` XML with a `<saml:NameID>victim@company.com</saml:NameID>` and any `<Signature>X</Signature>` tag.
4. Base64-encode the XML.
5. POST to `/api/sso/saml/:companyId/acs` with `SAMLResponse=<base64>` and `RelayState=<stolen>`.
6. Observe session cookie set for victim's account.

## Recommendation

Replace the stub with a proper XML signature validator such as `xml-crypto` or `samlify`. Minimum requirements:
- Validate the `<ds:Signature>` element against the configured IdP certificate using the `xml-crypto` library.
- Validate the assertion's `<Conditions>` (NotBefore / NotOnOrAfter) against current time.
- Validate the `<AudienceRestriction>` matches the SP entity ID.
- Reject unsigned assertions.
- Reject responses missing a certificate if `config.certificate` is set.

This is a known-incomplete implementation (the comment "In production, use a full XML signature validator" confirms it) that must not be deployed in production SSO scenarios.
