## Description

The `boardMutationGuard` is the primary CSRF protection for all board user mutations. It accepts a request as trusted if:

```typescript
function trustedOriginsForRequest(req: Request) {
  const origins = new Set(DEFAULT_DEV_ORIGINS.map(...));  // localhost:3100
  const host = req.header("host")?.trim();
  if (host) {
    origins.add(`http://${host}`.toLowerCase());
    origins.add(`https://${host}`.toLowerCase());
  }
  return origins;
}
```

The trusted origin set is **dynamically constructed from the `Host` header of the incoming request**. This means:

1. If an attacker can control the `Host` header (e.g., by exploiting a host header injection vulnerability at a load balancer, or via a misconfigured reverse proxy that passes client-supplied `Host` values), they can add their own origin to the trusted set.
2. The `Origin` header check passes if `origin === http://${host}` — attacker sets `Host: evil.com` and `Origin: http://evil.com` and the guard passes.
3. There is also a `Referer`-based fallback, which is easier to forge or omit in some browser contexts.

The guard also entirely bypasses for `local_implicit` actors (dev mode), which is correct, but the comment at line 51–56 notes that even multipart uploads from localhost are exempt, widening the local attack surface.

The guard only applies to `req.actor.type === "board"`. Agent requests (`type === "agent"`) bypass the guard entirely (by design), but this means a stolen agent token can be used for any mutation without CSRF concern — a separate risk vector.

## Impact

- If `Host` header injection is possible at the infrastructure layer, CSRF protection can be bypassed for any board user mutation.
- Without `SameSite=Strict` cookies (BetterAuth defaults to `Lax`), cross-site requests from `SameSite=Lax`-exempted navigational contexts (GET-initiated link navigation) could still carry cookies.
- The double-submit cookie pattern is not implemented — there is no cryptographic token to verify.

## Reproduction

1. Set up a reverse proxy that forwards the client-supplied `Host` header without restriction.
2. Craft a cross-origin POST request with `Host: attacker.com` and `Origin: http://attacker.com`.
3. The guard computes `trustedOrigins` to include `http://attacker.com`, accepts the request.

## Recommendation

- Replace the dynamic Host-based origin computation with a static allowlist derived from `config.allowedHostnames` (already built for the `privateHostnameGuard`).
- Consider implementing a standard CSRF double-submit cookie or synchronizer token pattern for state-mutating board operations.
- For the SSO ACS endpoint (sets session cookie on redirect): ensure `SameSite` is set to at least `Lax` (currently done) and verify the redirect-to-`/` behavior does not expose CSRF vectors for subsequent requests.
