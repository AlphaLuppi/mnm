## Description

When `MNM_E2E_SEED=true`, two separate disabling mechanisms activate:

1. **All Express rate limiters disabled** (`rate-limit.ts:118–121`):
```typescript
const isE2eMode = process.env.MNM_E2E_SEED === "true";
return async (req, res, next) => {
  if (isE2eMode) { next(); return; }
```
This flag is read at _middleware creation time_, not per request. Every `createRateLimiter()` call across the entire codebase — including MCP OAuth limiters, the global API limiter, and the SSO endpoints — reads this flag once and permanently disables itself.

2. **BetterAuth's built-in rate limit disabled** (`better-auth.ts:241`):
```typescript
...(isE2eMode ? { rateLimit: { enabled: false } } : {}),
```

Additionally, `MNM_E2E_SEED=true` activates the `/api/e2e-seed/*` routes, which perform privileged operations (granting `instance_admin`, seeding companies, etc.) with **no authentication check** — the endpoints check `isE2eEnabled()` but do not verify the caller's identity.

**If an operator accidentally sets `MNM_E2E_SEED=true` in a production deployment** (e.g., from a copied CI config or Docker Compose file), the result is:
- All rate limiting removed from sign-in, sign-up, OAuth token, and all other auth endpoints.
- Unauthenticated privilege-escalation endpoints exposed at `/api/e2e-seed/ensure-access`.
- Brute-force attacks against passwords are unconstrained.

## Impact

- Password brute-force with no rate limiting on `POST /api/auth/sign-in/email`.
- Unauthenticated attacker calls `POST /api/e2e-seed/ensure-access` with any userId to grant themselves `instance_admin` and membership in all companies.
- Complete instance compromise in one request if `MNM_E2E_SEED=true` in prod.

## Reproduction

1. Set `MNM_E2E_SEED=true` on a running server (or confirm it's set in a misconfigured prod deployment).
2. `POST /api/e2e-seed/ensure-access` with `{ userId: "<your-userId>" }` → receive `instance_admin` role.
3. Or brute-force `POST /api/auth/sign-in/email` with no throttling.

## Recommendation

- Add a startup guard: if `MNM_E2E_SEED=true` AND `deploymentMode=authenticated`, throw an error and refuse to start.
- Alternatively, reject `MNM_E2E_SEED=true` unless `NODE_ENV=test`.
- The e2e-seed routes should at minimum require an authenticated session with `instance_admin` role, even in E2E mode.
- Consider a separate `MNM_E2E_NO_RATELIMIT=true` flag instead of piggybacking on `MNM_E2E_SEED`.

**Commit** : TBD
**Fix description** : Added a fail-fast boot guard in `server/src/index.ts` immediately after `loadConfig()`: if `MNM_E2E_SEED === "true"` and `config.deploymentMode === "authenticated"`, the process throws `FATAL: MNM_E2E_SEED must NEVER be set in authenticated mode`. This prevents any authenticated deployment from inadvertently inheriting E2E test environment variables that disable rate limiting and expose unauthenticated admin routes.
