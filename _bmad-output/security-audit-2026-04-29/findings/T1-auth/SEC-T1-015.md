## Description

The SAML callback handler validates the relay state only when it is present in the request:

```typescript
async function handleSamlCallback(
  companyId: string,
  samlResponse: string,
  relayState?: string,
): Promise<SsoAuthResult> {
  // Validate relay state if present
  if (relayState) {
    const stored = ssoStateStore.get(relayState);
    if (!stored || stored.companyId !== companyId || stored.provider !== "saml") {
      throw unauthorized("Invalid SSO state");
    }
    ssoStateStore.delete(relayState);
  }
  // ← No else branch: absent relay state is fully accepted
```

If an IdP sends a SAML response without a `RelayState` (which is permitted by the SAML spec), the callback proceeds with no CSRF protection at all. An attacker can POST a forged SAML assertion (using the forged XML from SEC-T1-002) directly to `/api/sso/saml/:companyId/acs` without needing to obtain a relay state first.

The route handler at `sso-auth.ts:48–98` extracts `RelayState` from `req.body.RelayState as string | undefined` and passes it directly. A request with no `RelayState` body field will call `handleSamlCallback` with `relayState=undefined`, skipping the state store check.

Even if SEC-T1-002 were fixed (proper signature validation), the missing relay state would still allow relay attacks: an IdP that returns responses without a RelayState could have its responses replayed to authenticate as any user whose email the IdP knows.

## Impact

- Combined with SEC-T1-002, an attacker can forge a SAML assertion without needing a relay state at all.
- Even with proper signature validation, a response from a legitimate IdP can be replayed across sessions if relay state is absent.

## Recommendation

- Make relay state mandatory: if `relayState` is absent, reject the callback with `unauthorized("Missing relay state")`.
- Update the SAML AuthnRequest to require `RelayState` in the IdP response.
