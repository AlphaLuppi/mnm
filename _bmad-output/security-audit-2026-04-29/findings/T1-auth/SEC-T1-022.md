## Description

The `x-mnm-run-id` header is accepted from any client and injected into `req.actor.runId`:

```typescript
const runIdHeader = req.header("x-mnm-run-id");
// ... later ...
runId: runIdHeader ?? undefined,
```

This header is not validated (no UUID format check), not used for authorization decisions, and only used for tracing/audit correlation purposes.

**No security issue exists** in the current code. The `runId` is not used in any authorization gate, not checked against the agent's claimed `run_id` in its JWT, and not used to bypass any permission check.

A potential concern: if future code inadvertently uses `req.actor.runId` for access decisions, this header becomes an injection vector since it is entirely client-controlled.

The JWT `run_id` claim in agent tokens is also read by the verifier (`agent-auth-jwt.ts:118`) and placed in `req.actor.runId` as a fallback (`runId: runIdHeader || claims.run_id`). The client-supplied header overrides the JWT claim, which is noteworthy — an agent client can claim any run_id regardless of what's in its token.

## Impact

Informational — no current security impact. Future code changes that use `runId` for authorization should be reviewed.

## Recommendation

- Add a comment to `req.actor.runId` warning that this value is client-controlled and must not be used for authorization.
- Optionally validate the header format as a UUID if the run ID is expected to be a UUID.
- Consider renaming to `runIdHint` to signal its informational-only nature.
