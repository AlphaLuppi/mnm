## Description

The OIDC callback handler (`handleOidcCallback`) exchanges the authorization code for tokens and then extracts user claims from the `id_token` JWT by decoding its base64 payload **without verifying the signature**:

```typescript
if (tokenData.id_token) {
  try {
    const payload = JSON.parse(
      Buffer.from(tokenData.id_token.split(".")[1]!, "base64").toString("utf-8"),
    ) as { email?: string; name?: string; preferred_username?: string; sub?: string };
    email = payload.email ?? payload.preferred_username ?? null;
    name = payload.name ?? null;
  } catch {
    // id_token decode failed, try userinfo
  }
}
```

There is no call to a JWKS endpoint, no RS256 / ES256 signature validation, no `iss` check, no `aud` check, and no `exp` check on the id_token itself (the token exchange step checks the HTTP response status, but not the token's own claims).

The `tokenData` comes from a server-side POST to the configured `tokenUrl` — this path is controlled by the OIDC configuration stored in the database. If an admin misconfigures `config.tokenUrl` to point to an attacker-controlled server, or if the upstream IdP is compromised, a forged id_token with an arbitrary `email` will be fully trusted.

Additionally, there is no PKCE on the OIDC SSO flow (the MCP OAuth flow uses PKCE correctly, but the SSO OIDC flow at `services/sso-auth.ts:196–203` does not add `code_challenge` to the authorization request).

## Impact

- Trust in the id_token identity is entirely delegated to the correctness of the token exchange step.
- A misconfigured or malicious `tokenUrl` could issue forged id_tokens, leading to account takeover.
- Absence of PKCE means the OIDC authorization code is vulnerable to interception if the `redirect_uri` is over HTTP or if there is a referrer leak.
- `iss` and `aud` are never validated, violating OIDC Core 1.0 §3.1.3.7.

## Reproduction

1. Configure OIDC SSO with a `config.tokenUrl` pointing to an attacker-controlled server that returns an id_token with `{"email":"admin@company.com","sub":"attacker"}` (unsigned, any three-part JWT).
2. Initiate the OIDC login flow for the target company.
3. Complete the redirect back to the callback — the attacker server returns the forged token.
4. Session is created for `admin@company.com`.

## Recommendation

- Use a proper OIDC client library (`openid-client`) that validates `iss`, `aud`, `exp`, `nonce`, and signature by fetching JWKS from the IdP's discovery document.
- Add PKCE (`code_challenge` + `code_verifier`) to all OIDC authorization requests originating from the SSO service.
- Validate `id_token.aud` matches the registered `clientId`.
- Validate `id_token.iss` matches the expected issuer from the configuration.
