## Description

Two critical authorization middlewares contain unconditional `isInstanceAdmin` bypasses:

**1. `assertCompanyMembership` (company-access.ts:39):**
```typescript
if (req.actor.source === "local_implicit" || req.actor.isInstanceAdmin) {
  next();
  return;
}
```
An `isInstanceAdmin` user can access **any company's data** regardless of membership. The multi-tenant isolation promise is broken for instance admins.

**2. `requirePermission` (require-permission.ts:167):**
```typescript
if (req.actor.isInstanceAdmin) return;
```
Instance admins bypass all RBAC permission checks — they can perform any action in any company.

This is not inherently wrong for a super-admin pattern, but several security concerns arise:

- **`isInstanceAdmin` is set from DB at every request** (`middleware/auth.ts:46–48`) — a DB query that checks `instanceUserRoles` table. This is correct. However, a compromised session for any instance admin account grants full access to all tenants.
- **No audit trail differentiation**: instance admin actions bypass `requirePermission`, which means the `access.denied` audit events are not generated for them. Any admin-abused action is harder to detect.
- **Board claim auto-promotes first signup**: the `databaseHooks.user.create.after` hook in `better-auth.ts:248–261` promotes the first-ever user to `instance_admin` automatically. This "first-user bootstrap" logic is safe in isolation but could be exploited in a race condition (two simultaneous sign-ups) — though the `WHERE NOT EXISTS` guard makes this atomic.

## Impact

- A compromised instance admin session gives complete read/write access to all companies and all data on the instance.
- Post-compromise forensics is impaired because admin actions bypass the permission check layer's audit events.

## Reproduction

1. Obtain an instance admin session (e.g., via SEC-T1-001 or SEC-T1-005).
2. Access any company's data (`/companies/<any-uuid>/agents`) — request succeeds without membership.
3. Perform any permission-gated action without restriction.

## Recommendation

- Scope instance admin privileges: create a separate `super_admin_access` permission checked explicitly for cross-tenant reads, rather than bypassing all membership checks.
- Emit explicit audit events when instance admin exercises cross-tenant or elevated access (log that the bypass was invoked, not just the action).
- Implement "just-in-time" elevation: require instance admins to explicitly activate their admin privilege for a session (time-limited), rather than having it active on every request.
- Consider breaking the single `isInstanceAdmin` flag into finer-grained instance-level permissions (e.g., `instance:read`, `instance:manage_users`, `instance:manage_companies`).
