## Description

The admin password reset endpoint (`POST /companies/:companyId/members/:userId/reset-password`) generates a temporary password as follows:

```typescript
const tempPassword = randomBytes(6).toString("base64url");
```

This generates 6 bytes = 48 bits of entropy, base64url-encoded to approximately 8 characters. The concerns are:

**1. Low entropy.** NIST SP 800-63B recommends a minimum of 64 bits of entropy for machine-generated temporary credentials. 48 bits is within brute-force range given hardware acceleration against bcrypt (bcrypt hash is what gets stored). The password is used directly as a credential until the user changes it.

**2. Returned in plaintext response.** The generated password is returned to the admin in the HTTP response JSON body (`res.json({ temporaryPassword: tempPassword })`). If the API response is logged (e.g., by the HTTP access logger at the proxy level or in any audit system), the temporary password appears in logs in clear text.

**3. No expiration.** The temporary password is set in `authAccounts.password` with no TTL. It remains valid indefinitely until the user changes it. There is no "must change password on next login" flag.

**4. No invalidation of existing sessions.** Setting a new temporary password does not invalidate the target user's existing sessions. The user's old sessions remain active.

## Impact

- Temporary passwords can be brute-forced or guessed within reasonable time.
- If API responses or proxy logs capture response bodies, temporary passwords are exposed in plaintext.
- Accounts remain in a temporary-password state indefinitely, increasing the attack window.

## Reproduction

1. Admin calls `POST /companies/:id/members/:userId/reset-password`.
2. Response contains `temporaryPassword: "abc12345"` (8 chars of base64url).
3. Attacker with access to server logs or a compromised admin session retrieves the password.
4. Logs into the target account.

## Recommendation

- Increase entropy to at least 16 bytes (`randomBytes(16).toString("base64url")` → 22 chars, 128 bits).
- Never include the temporary password in response logs. Consider returning it only once (consistent with current behavior) but ensure the server-side HTTP access logger is configured to redact response bodies for this endpoint.
- Add a `passwordResetRequired: true` flag to the user record, enforced at sign-in to require immediate password change.
- Invalidate all existing sessions for the target user when a temporary password is set.
