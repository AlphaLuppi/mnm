## Description

BetterAuth's account linking is configured with `allowDifferentEmails: true`:

```typescript
account: {
  accountLinking: {
    enabled: true,
    trustedProviders: ["gitlab", "microsoft"],
    allowDifferentEmails: true,
  },
},
```

With this flag, a user authenticated via email+password can link their account to any GitLab or Microsoft OAuth identity — even if the OAuth email does not match the email+password account. The comment justifies this as needed because "a user's MnM email often differs from their GitLab/Entra email."

**Threat model:**
- The OAuth flow is initiated from an already-authenticated MnM session (correct — the user must be logged in before linking).
- However, if an attacker controls a GitLab or Microsoft OAuth app registered on the same IdP, or if they share a machine with a logged-in victim and initiate the link flow from a different browser tab, the email mismatch guard no longer prevents linking an unrelated identity to the victim's account.
- More critically: once linked, the attacker can use _their own_ GitLab/Microsoft identity to log into the victim's MnM account at any future time (since BetterAuth's social login will now auto-link to the existing account).

The attack surface is elevated because both GitLab and Microsoft are listed as `trustedProviders`, meaning even before the user explicitly consents to linking, BetterAuth may auto-link on email match. With `allowDifferentEmails: true`, auto-linking on email match is disabled — but **manual linking on mismatch is explicitly enabled.**

## Impact

- If an attacker can initiate a social link from a victim's active session (e.g., via CSRF — though the boardMutationGuard partially mitigates this), they can permanently link their OAuth identity to the victim's account.
- Once linked, the attacker authenticates as the victim at any future time with no password required.

## Reproduction

1. Victim is logged in with email+password.
2. Attacker initiates a `link-social` request (POST `/api/auth/link-social`) with `provider: "gitlab"` via a CSRF or hijacked session.
3. Attacker completes GitLab OAuth in their own browser (callback goes to MnM with attacker's GitLab identity).
4. Because `allowDifferentEmails: true`, BetterAuth links attacker's GitLab account to victim's MnM account.
5. Attacker can now log in as victim via GitLab OAuth at any time.

## Recommendation

- Evaluate whether `allowDifferentEmails: true` is strictly necessary. The stated justification (work email vs. GitLab LDAP alias) could instead be solved by:
  - Providing an admin override to manually merge duplicate accounts.
  - Requiring the user to explicitly confirm the email mismatch during the link flow UI.
- If `allowDifferentEmails` must remain, add a server-side confirmation step (send an email to the existing account's address before completing the link).
- Ensure `link-social` endpoints are protected against CSRF (the `boardMutationGuard` checks Origin/Referer, but this should be explicitly audited for this specific flow).
