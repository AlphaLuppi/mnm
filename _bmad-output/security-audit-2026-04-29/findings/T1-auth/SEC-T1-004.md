## Description

The SSO auth service creates sessions by directly inserting rows into the `authSessions` table (`createSsoSession`), bypassing BetterAuth's session management entirely. The session token is set as a cookie named `better-auth.session_token` — the same cookie name BetterAuth uses — so the UI treats it as a regular BetterAuth session.

Three problems follow from this approach:

**1. No session regeneration on SSO login.**
The session token is generated at SSO callback time and immediately written. There is no concept of a pre-login session that gets regenerated to a new ID after authentication succeeds. This is a textbook session fixation vector if any code issues a session ID before auth completes (e.g., for tracking state).

**2. BetterAuth cannot revoke these sessions.**
When a user logs out via BetterAuth's `/api/auth/sign-out`, BetterAuth invalidates rows in `authSessions` using its own session ID format. SSO-created sessions use raw token bytes as the session token and BetterAuth's lookup may not find them (depending on how BetterAuth keys sessions internally). The result is a stale SSO session that persists after "sign out."

**3. Session lifetime is hardcoded to 30 days with no max-session limits.**
The `createSsoSession` function always creates a 30-day session (`expiresAt = Date.now() + 30 * 24 * 60 * 60 * 1000`). There is no check for concurrent active sessions per user, no limit on total SSO sessions, and no revocation mechanism if the SSO IdP is disconnected or the user's access is revoked at the IdP level.

## Impact

- A user whose SSO access is revoked at the IdP level will retain a valid MnM session for up to 30 days.
- Sign-out may be incomplete for SSO users — session cookie is cleared client-side but the DB row remains valid and would be re-accepted if replayed.
- Session fixation risk in multi-step flows.

## Reproduction

1. Log in via SAML or OIDC SSO.
2. Sign out via the normal BetterAuth UI flow (`/api/auth/sign-out`).
3. Re-send the original session cookie that was set during SSO login.
4. Check if the session is still accepted (depends on BetterAuth internals but the DB row is likely still present).

## Recommendation

- Route SSO-created sessions through BetterAuth's official session creation API rather than inserting directly into the DB.
- Implement a session revocation check at login to invalidate all existing active sessions for the user when a new SSO login occurs (force fresh start).
- Add a maximum concurrent SSO sessions limit per user.
- Periodically re-validate SSO sessions against the IdP (e.g., by checking the SSO session expiry or issuing short-lived tokens requiring frequent IdP re-authentication).
