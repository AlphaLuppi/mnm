## Description

The `invites` table has a special RLS policy that allows rows with NULL `company_id`:

```sql
-- 16. invites (NULLABLE company_id — special policy: allow NULL company_id rows)
CREATE POLICY "tenant_isolation" ON "invites" AS RESTRICTIVE FOR ALL 
  USING (company_id = current_setting('app.current_company_id', true)::uuid OR company_id IS NULL);
```

This means: **any company's RLS context will see ALL invites that have NULL company_id**.

If the `invites` table contains any rows with `company_id IS NULL` (e.g., instance-wide invitations, or invites from before company_id was populated), ALL tenants will see those rows.

The use case for NULL company_id invites needs to be audited:
1. Are there legitimately global invites in production data?
2. Can an attacker create an invite with NULL company_id and thus have it visible to every tenant?
3. Does the invite creation code enforce company_id?

## Impact

**LOW.** If NULL company_id invites exist in production (e.g., from the initial instance setup or admin-level invitations), they are visible to ALL companies. An attacker could use a leaked invite token from company A to join company B if the invite has NULL company_id.

## Recommendation

1. Audit production data for any `invites` rows with `company_id IS NULL`
2. If such rows exist for legitimate reasons, add a separate `instance_invites` table or an explicit `is_global` boolean
3. Consider removing the `OR company_id IS NULL` clause and adding a separate policy for global invites that restricts access to instance admins only

## Fix

Migration `0071_security_audit_rls_hardening.sql` — `DROP POLICY IF EXISTS "tenant_isolation" ON "invites"` followed by a new `CREATE POLICY` without the `OR company_id IS NULL` clause. Audit of the codebase confirmed no code path creates invites with NULL `company_id`; the nullable column is a schema artefact. The RESTRICTIVE policy now requires an exact `company_id` match.
