## Description

The `oauth_clients` table has **no `company_id` column**:

```sql
CREATE TABLE oauth_clients (
  client_id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  client_secret TEXT,
  client_name TEXT NOT NULL,
  redirect_uris JSONB NOT NULL DEFAULT '[]'::jsonb,
  grant_types JSONB NOT NULL DEFAULT '[]'::jsonb,
  created_at TIMESTAMPTZ NOT NULL DEFAULT now()
);
```

OAuth clients are instance-global. Any `client_id` registered in the system can potentially be used to obtain tokens for any company's users — there is no company scoping on the client registration.

`oauth_refresh_tokens` has a `company_id` column but no RLS (already flagged in SEC-T2-001). This means:
1. An attacker who obtains a refresh token for any company can use the `oauth_clients` global registration to attempt token exchange
2. The refresh token table has no DB-level guard preventing cross-company token listings

The MCP OAuth flow (in `server/src/mcp/auth/`) creates tokens with `company_id` embedded in claims, but the client registration itself is company-agnostic, creating a systemic design inconsistency.

## Impact

**HIGH.** In a multi-tenant B2B environment, OAuth client registrations should be company-scoped. A global client registry means:
1. A compromised or malicious OAuth client registered by one company admin has visibility into all registered clients
2. The consent flow (`mcp-consent.ts`) must be carefully checked to ensure it does not allow a client to request scopes across company boundaries
3. Future OAuth flows (authorization code, device flow) would need to enforce company isolation at the client level

## Reproduction

1. Register OAuth client A in Company A's admin UI
2. Query `SELECT * FROM oauth_clients` directly — returns ALL companies' OAuth clients
3. Use client A to initiate an OAuth flow for a Company B user

## Recommendation

Add `company_id` to `oauth_clients`:
```sql
ALTER TABLE oauth_clients ADD COLUMN company_id UUID NOT NULL REFERENCES companies(id);
ALTER TABLE oauth_clients ENABLE ROW LEVEL SECURITY;
ALTER TABLE oauth_clients FORCE ROW LEVEL SECURITY;
CREATE POLICY "tenant_isolation" ON "oauth_clients" AS RESTRICTIVE FOR ALL
  USING (company_id = current_setting('app.current_company_id', true)::uuid);
```

Also add RLS to `oauth_refresh_tokens` (covered in SEC-T2-001).

## Decision: wontfix — intentional instance-global design

`oauth_clients` is the MCP OAuth client registry used by Claude Desktop and MCP SDK clients. Client registration is an instance-level operation: one `client_id` is shared across all companies, and the OAuth consent flow in `mcp-consent.ts` enforces company isolation at the token layer (every token carries a `company_id` claim, and `oauth_refresh_tokens` now has RESTRICTIVE RLS on `company_id` — see SEC-T2-001 fix).

Adding `company_id` to `oauth_clients` would require each company admin to re-register the same MCP client, breaking the MCP discovery handshake which is by design instance-scoped (`/mcp` endpoint is not company-prefixed). 

The remaining risk (enumeration of client IDs across companies) is low because `client_id` UUIDs are not sensitive on their own; the `client_secret` is the credential, and it is only returned at registration time.
