## Description

Many agent routes follow this pattern:

```typescript
router.get("/companies/:companyId/agents/:id", async (req, res) => {
  const id = req.params.id as string;
  const agent = await svc.getById(id);       // fetches agent by ID only
  if (!agent) {
    res.status(404).json({ error: "Agent not found" });
    return;
  }
  assertCompanyAccess(req, agent.companyId); // validates against agent's REAL companyId
  // ...
});
```

The path parameter `req.params.companyId` (from `/companies/:companyId/agents/:id`) is **never compared against `agent.companyId`**.

**This means:**
1. Attacker in Company A sends: `GET /api/companies/<company-A-uuid>/agents/<company-B-agent-uuid>`
2. RLS context is set to `company-A-uuid` (attacker's company)
3. `getById` queries `agents` table: **RLS blocks this** since `company-A-uuid != company-B-agent-uuid` — returns null → 404

So the RLS layer saves us here. BUT:

**The vulnerability is latent:** If RLS is ever disabled, misconfigured, or tables are queried without the RLS context (e.g., in a background job that forgets to set context), `assertCompanyAccess(req, agent.companyId)` would validate against the agent's real company, not the path company. A board user in Company A who also has access to Company B could access Company B agents by putting Company A's companyId in the path.

More concretely: there is a **path confusion** attack:
- User is member of both Company A and Company B
- `req.params.companyId = company-A`  
- `agent.companyId = company-B`
- `assertCompanyAccess(req, agent.companyId)` → checks if user is in company-B → YES
- Access GRANTED, but the RLS context was set for company-A
- The subsequent service calls (e.g. `listConfigRevisions(id)`) run with company-A's RLS context

This creates a state where the permission check uses `agent.companyId` but DB queries run under a different tenant context.

## Impact

**HIGH.** The path companyId and the agent's real companyId can diverge without triggering a rejection. For users with multi-company memberships, this means:
1. Mixed RLS context: auth check passes for company-B but queries run under company-A context
2. The `assertAgentTagVisible` uses `agent.companyId` but queries tag filter using that company's data — potentially mixing tag scope between companies
3. Audit logs record `companyId = agent.companyId` which may differ from the URL company

## Reproduction

1. User has membership in both Company A and Company B
2. GET `/api/companies/<company-A-id>/agents/<company-B-agent-id>`
3. RLS context = Company A; auth check passes because user is in Company B; inconsistent state

## Recommendation

Add an explicit check that the path companyId matches the agent's company:

```typescript
router.get("/companies/:companyId/agents/:id", async (req, res) => {
  const companyId = req.params.companyId as string;
  const id = req.params.id as string;
  const agent = await svc.getById(id);
  if (!agent || agent.companyId !== companyId) { // EXPLICIT CHECK
    res.status(404).json({ error: "Agent not found" });
    return;
  }
  assertCompanyAccess(req, companyId); // use PATH companyId, not agent.companyId
  // ...
});
```

This pattern should be applied consistently to ALL routes that fetch by ID and then access-check against the fetched record's companyId.
