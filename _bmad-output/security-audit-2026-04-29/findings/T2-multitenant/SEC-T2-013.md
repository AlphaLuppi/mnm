## Description

The `llmRoutes` are mounted directly on the app (not the `api` Router) and **before** the `api` Router:

```typescript
// app.ts
app.use(llmRoutes(db));  // mounted at app level, before /api router
// ...
app.use("/api", api);   // api router with rate limiter + company middleware
```

This means:
1. `/llms/agent-configuration.txt` and `/llms/agent-icons.txt` bypass the API rate limiter
2. These routes bypass `boardMutationGuard`
3. These routes do NOT have the `/companies/:companyId` prefix — they're company-agnostic information endpoints

The routes do perform their own auth check via `assertCanRead`:
```typescript
async function assertCanRead(req: Request) {
  if (req.actor.type === "board") return;
  if (req.actor.type !== "agent" || !req.actor.agentId) {
    throw forbidden("Board or permitted agent authentication required");
  }
  const actorAgent = await agentsSvc.getById(req.actor.agentId);
  if (!actorAgent || !hasCreatePermission(actorAgent)) {
    throw forbidden("Missing permission");
  }
}
```

However: `agentsSvc.getById(req.actor.agentId)` at this point has NO RLS context set (because the tenant middleware hasn't run). The RLS context would be whatever was left on the pooled connection from the last request (potentially another company's context, or empty).

If `agentsSvc.getById` returns null due to empty RLS context, a legitimate agent gets a 403. If it returns a stale company's agent due to wrong RLS context, a wrong agent's permissions are checked.

## Impact

**LOW.** The routes expose generic information (adapter list, icon names) that is not sensitive. The auth bypass window is narrow. But the architecture inconsistency could matter if these routes ever expose company-specific data.

## Recommendation

Move `llmRoutes` inside the `api` Router or at minimum after `actorMiddleware`. Add the same rate limiter. Consider namespacing under `/api/llms/` to benefit from the API middleware chain.
