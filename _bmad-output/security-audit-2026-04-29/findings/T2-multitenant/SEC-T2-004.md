## Description

The `tenantContextMiddleware` sets the PostgreSQL RLS context using `is_local=false` (session-scoped, not transaction-scoped):

```typescript
// tenant-context.ts:64
await db.execute(sql`SELECT set_config('app.current_company_id', ${companyId}, false)`);
```

The `false` argument means the setting **persists for the entire database connection session**, not just the current transaction. This is by design (the comment says "persists for the session so subsequent queries on the same pooled connection see the value").

The cleanup is registered on `res.on('close')` and `res.on('finish')`. The problem:

**The cleanup fires ASYNCHRONOUSLY after the response is sent.** The postgres.js pool (`max: 40`) immediately returns the connection to the pool. A new request from a DIFFERENT tenant could acquire the same connection before the cleanup fires.

Timeline:
1. Request R1 (Company A): `set_config('app.current_company_id', 'company-A-uuid', false)` — context set
2. Response sent → `res.finish` event registered but not yet fired
3. Connection returned to pool
4. Request R2 (Company B) acquires the same connection — `current_company_id` is still `company-A-uuid`
5. `set_config('app.current_company_id', 'company-B-uuid', false)` runs — now correct
6. Company A cleanup finally fires: `set_config('app.current_company_id', '', false)` — CLEARS company B's context mid-request!

Additionally:
- The cleanup is registered on both `close` and `finish` (deduplication via `cleanupRan` flag) but runs fire-and-forget (`clearTenantContext(db).catch(...)`)
- `clearTenantContext` acquires a connection from the pool to execute the reset — this may be a DIFFERENT connection than the one that had the context set

The pool uses `postgres-js` with `max: 40, idle_timeout: 30`. Each physical connection is independent. The `set_config` call sets the context on whichever connection the pool allocates. The cleanup call may go to a different physical connection.

## Impact

**HIGH.** Under high concurrency (40+ simultaneous requests), there is a window where:
1. A Company A request's cleanup clears the context on Company B's connection mid-query, causing Company B's RLS to filter to `company_id = ''::uuid`, returning zero results (data unavailability, not data leak).
2. OR: Company B's `set_config` hasn't run yet when a query executes on the connection just returned by Company A → RLS context still Company A → data leak.

The risk is elevated because the server uses a 40-connection pool and handles concurrent requests.

## Reproduction

High-concurrency load with two companies making simultaneous requests. The window is narrow but real under load.

## Recommendation

**Use transaction-scoped context (`is_local=true`)** inside a transaction for all tenant queries:

```typescript
// Instead of session-scoped set_config, wrap each request's DB queries in a transaction
await db.transaction(async (tx) => {
  await tx.execute(sql`SELECT set_config('app.current_company_id', ${companyId}, true)`);
  // All queries in this transaction see the correct context
  // Auto-cleared when transaction ends (is_local=true)
  next(); // pass tx to req
});
```

This is a larger refactor. A simpler mitigation: ensure every sensitive query **also** includes an explicit `WHERE company_id = $companyId` even when RLS is active (defense in depth at query level).
