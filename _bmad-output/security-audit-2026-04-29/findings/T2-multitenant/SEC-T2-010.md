## Description

The HTTP API endpoints have a rate limiter configured in `app.ts`:

```typescript
const apiRateLimiter = createRateLimiter({
  windowMs: 60_000,
  max: 500,
  keyGenerator: (req) => `${companyId}:${actorId}`,
});
api.use(apiRateLimiter);
```

However, WebSocket upgrade requests (`/api/companies/:companyId/events/ws` and `/ws/chat/:channelId`) bypass this rate limiter entirely because:
1. They are handled by the Node.js `server.on('upgrade', ...)` event listener, not by Express middleware
2. The `apiRateLimiter` only applies to Express routes, not raw HTTP upgrade requests

There is no rate limiting on:
- Number of WS upgrade attempts per IP or per company
- Number of concurrent WS connections per user
- Authentication attempt rate on WS upgrades (brute force of agent API keys via WS)

Additionally, MCP sessions (`/mcp`) have separate limiters but the `mcpExistingSessionLimiter` keys on the session ID header (not on actor/company), so a flood of unique session IDs would be treated as new sessions, each limited to 10/minute/IP by `mcpNewSessionLimiter` but this only partially mitigates.

## Impact

**MEDIUM.** An attacker can:
1. Open unlimited WebSocket connections from multiple IPs, consuming server file descriptors and memory
2. Enumerate agent API keys by attempting WS auth at high rate without being rate-limited
3. Flood the live-events WS server's `subscribeCompanyLiveEvents` subscription system

## Recommendation

Add rate limiting on WS upgrade requests before auth:

```typescript
// In server.on('upgrade', ...) handler
const upgradeKey = `ws-upgrade:${req.socket.remoteAddress ?? 'unknown'}`;
if (await rateLimitStore.isLimited(upgradeKey, { max: 20, windowMs: 60_000 })) {
  rejectUpgrade(socket, "429 Too Many Requests", "rate limited");
  return;
}
```

Also add a per-company connection count limit to prevent a single tenant from exhausting connections.
