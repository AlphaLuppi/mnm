## Description

The `user_pods` and `artifact_deployments` tables have RLS policies that use `::text` comparison instead of `::uuid`:

```sql
-- user_pods
CREATE POLICY user_pods_rls ON user_pods 
  USING (company_id::text = current_setting('app.current_company_id', true));
  
-- artifact_deployments  
CREATE POLICY artifact_deployments_rls ON artifact_deployments 
  USING (company_id::text = current_setting('app.current_company_id', true));
```

Compare to the standard pattern used in the 0030 migration (all other 41 tables):
```sql
CREATE POLICY "tenant_isolation" ON "agents" AS RESTRICTIVE FOR ALL 
  USING (company_id = current_setting('app.current_company_id', true)::uuid);
```

Differences:
1. **Not RESTRICTIVE**: The new policies are permissive (default), not `AS RESTRICTIVE`. A permissive policy allows access if the condition is TRUE **or if any other permissive policy grants access**. A restrictive policy must pass even if other policies would grant access.
2. **Text comparison**: `company_id::text = current_setting(...)` instead of `company_id = current_setting(...)::uuid`. UUID comparison in PostgreSQL is exact; text comparison could theoretically be case-insensitive or have edge cases with special UUID formats.
3. **Different policy name**: `user_pods_rls` vs `tenant_isolation` — inconsistency could complicate security audits.

The absence of `AS RESTRICTIVE` is the more significant concern. In PostgreSQL, if a table has both a permissive and a restrictive policy, the restrictive policy MUST pass regardless of permissive policies. For `user_pods` and `artifact_deployments`, there are no other policies — so in practice, it behaves the same. But if a future migration adds another permissive policy (e.g., for service accounts), it could bypass the intended company isolation.

## Impact

**MEDIUM.** The current behavior is equivalent in isolation (no other policies exist on these tables), but the inconsistency is a latent risk. A future developer adding a service-account policy could unknowingly bypass the intended company isolation because the policy is permissive, not restrictive.

## Recommendation

Standardize RLS policies on `user_pods` and `artifact_deployments` to match the established pattern:

```sql
-- Drop old policies
DROP POLICY IF EXISTS user_pods_rls ON user_pods;
DROP POLICY IF EXISTS artifact_deployments_rls ON artifact_deployments;

-- Add RESTRICTIVE policies with UUID comparison
CREATE POLICY "tenant_isolation" ON "user_pods" AS RESTRICTIVE FOR ALL
  USING (company_id = current_setting('app.current_company_id', true)::uuid);

CREATE POLICY "tenant_isolation" ON "artifact_deployments" AS RESTRICTIVE FOR ALL
  USING (company_id = current_setting('app.current_company_id', true)::uuid);
```
