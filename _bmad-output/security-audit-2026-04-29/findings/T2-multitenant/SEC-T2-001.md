## Description

The following tables were added in migrations 0055–0063 and have NO PostgreSQL Row-Level Security (RLS) policy. All other tenant-scoped tables in the system enforce RLS via a RESTRICTIVE `tenant_isolation` policy using `app.current_company_id`. These 9 tables were added after migration 0030 (which set up RLS for 41 tables) and each was missed:

| Table | Migration | Has company_id? | Has RLS? |
|---|---|---|---|
| `routines` | 0055_routines.sql | YES | NO |
| `routine_triggers` | 0055_routines.sql | YES | NO |
| `routine_runs` | 0055_routines.sql | YES | NO |
| `feedback_votes` | 0056_feedback_votes.sql | YES | NO |
| `folder_shares` | 0056_folder_workspace.sql | YES | NO |
| `view_presets` | 0057_view_presets.sql | YES | NO |
| `user_widgets` | 0058_blocks_foundation.sql | YES | NO |
| `inbox_items` | 0059_inbox_items.sql | YES | NO |
| `oauth_refresh_tokens` | 0063_oauth_tables.sql | YES | NO |

The `agent_permissions` and `role_permissions` tables have no `company_id` column (they are join tables). These are discussed separately in SEC-T2-002.

## Impact

**CRITICAL — cross-company data leak.** RLS is the last-resort defense. If an attacker can set `app.current_company_id` to their own company but trigger a query path that hits these tables (e.g. via a compromised connection, a race on the pool, or any future code bug that skips the application-layer company check), they can read data from any tenant's routines, inbox items, widgets, view presets, folder shares, feedback votes, and OAuth refresh tokens.

The application layer does add `assertCompanyAccess` checks, but the defense-in-depth guarantee (RLS blocks even if app layer fails) is broken for these tables.

`oauth_refresh_tokens` is particularly sensitive: it stores active OAuth tokens with company_id and user_id. Without RLS, a bug in the OAuth path could expose another company's active tokens.

`inbox_items` are personal notifications; leaking them reveals workflow/activity data across company boundaries.

## Reproduction

1. Deploy MnM with two companies: Company A (attacker) and Company B (victim).
2. Create inbox items, routines, view presets in Company B.
3. As an attacker in Company A, if the RLS context is Company A but a direct DB query hits the `inbox_items` table (bypassing application-layer filters), all Company B inbox items are returned because no RLS policy filters them.

In the current architecture, the application-layer `assertCompanyAccess` provides the primary guard. But the defense-in-depth guarantee is absent.

## Recommendation

Add RLS to all 9 tables in a new migration. Use the same pattern as the main 0030 migration:

```sql
-- Example for routines
ALTER TABLE "routines" ENABLE ROW LEVEL SECURITY;
ALTER TABLE "routines" FORCE ROW LEVEL SECURITY;
CREATE POLICY "tenant_isolation" ON "routines" AS RESTRICTIVE FOR ALL 
  USING (company_id = current_setting('app.current_company_id', true)::uuid);

-- Repeat for routine_triggers, routine_runs, feedback_votes, folder_shares,
-- view_presets, user_widgets, inbox_items, oauth_refresh_tokens
```

## Fix

Migration `0071_security_audit_rls_hardening.sql` — ENABLE RLS + FORCE RLS + RESTRICTIVE `tenant_isolation` policy for all 9 tables. Same pattern as `0030_rls_policies.sql`.
