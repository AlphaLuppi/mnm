## Description

The `agent_permissions` and `role_permissions` join tables do not have a `company_id` column and therefore have no RLS policy. The migration comment for `role_permissions` explicitly states: "role_permissions: no company_id column -- RLS enforced via FK chain (role->company)".

The FK chain logic assumes that:
1. `roles` table has RLS → visible `role_id` values are already filtered to current company
2. `permissions` table has RLS → visible `permission_id` values are already filtered to current company

Therefore any join that includes these tables will naturally be scoped — IF the parent tables are properly filtered.

However, this has a critical assumption: **a direct SELECT on `agent_permissions` or `role_permissions` without joining the parent tables bypasses all company scoping entirely.** If any code path queries these tables directly without joining/filtering through the FK chain, it can see cross-company data.

Schema:
```typescript
// agent_permissions — no company_id
{ agentId: uuid, permissionId: uuid }

// role_permissions — no company_id  
{ roleId: uuid, permissionId: uuid }
```

## Impact

**HIGH.** Any query that does `SELECT * FROM agent_permissions` or `SELECT * FROM role_permissions` without proper join-based filtering will return data from all companies. Since these tables control which permissions agents and roles have, an attacker could:
1. Enumerate which permission UUIDs are assigned to agents/roles across companies (inferring security posture)
2. If combined with a bug in permission checking, escalate privileges cross-company

The risk is lower in the current codebase since the application layer uses Drizzle ORM with join-based queries, but the absence of a DB-level guard means a single coding mistake exposes all companies.

## Reproduction

Direct query against a running PostgreSQL instance with `app.current_company_id` set to any valid company:
```sql
SET app.current_company_id = '<company-a-uuid>';
SELECT * FROM agent_permissions; -- Returns ALL companies' agent permissions
SELECT * FROM role_permissions;  -- Returns ALL companies' role_permissions
```

## Recommendation

Option A (preferred): Add `company_id` column to both join tables and add proper RESTRICTIVE RLS policy, consistent with other tables.

Option B (acceptable): Add a RESTRICTIVE RLS policy using the FK chain:
```sql
-- For agent_permissions: filter via agents table (which <redacted-acronym> RLS)
ALTER TABLE "agent_permissions" ENABLE ROW LEVEL SECURITY;
ALTER TABLE "agent_permissions" FORCE ROW LEVEL SECURITY;
CREATE POLICY "tenant_isolation" ON "agent_permissions" AS RESTRICTIVE FOR ALL
  USING (
    agent_id IN (
      SELECT id FROM agents 
      WHERE company_id = current_setting('app.current_company_id', true)::uuid
    )
  );
```

## Fix

Migration `0071_security_audit_rls_hardening.sql` — Option B (FK-chain): ENABLE RLS + FORCE RLS + RESTRICTIVE policy using subquery on parent tables (`agents` and `roles` respectively, which already have RLS on `company_id`). No schema change to the join tables.
