## Description

The entire `/api` surface is protected by a single `createRateLimiter` instance:

```typescript
// app.ts:233
const apiRateLimiter = createRateLimiter({
  redisState: opts.redisState ?? null,
  windowMs: 60_000,
  max: 500,
  keyGenerator: (req) => {
    const companyId = req.params.companyId ?? "global";
    const actorId = ...;
    return `${companyId}:${actorId}`;
  },
});
```

**Problem 1 — Multi-instance bypass**: When Redis is unavailable or not configured, each server instance maintains its own in-memory `Map`. With N instances behind a load balancer, the effective rate limit is N×500. The fallback is silent (only `logger.warn`), so operators may not notice Redis is down while clients exploit the N-fold higher limit.

**Problem 2 — Key when `companyId` is not in path**: Routes mounted directly without `/companies/:companyId/` prefix (e.g., `GET /api/health`, `GET /llms/agent-configuration.txt`, `POST /board-claim/:token/claim`, `GET /invites/:token`) produce key `"global:${actorId}"`. Multiple actors hitting unauthenticated routes share `"global:unknown"`, meaning the 500-request window is shared across all unauthenticated traffic, not per-actor.

**Problem 3 — No per-IP global ceiling**: An unauthenticated client can make 500 requests/minute before hitting the `global:unknown` bucket. Every different IP or bearer token gets a fresh 500/min. There is no per-IP ceiling alongside the per-tenant ceiling.

**Problem 4 — No cost-based rate limit for LLM endpoints**: `POST /companies/:companyId/governed-workflows/:name/ai/chat` (AI assistant SSE) is extremely expensive but falls under the same flat 500 req/min limit as a GET request. The in-process concurrency limiter (3 per actor) mitigates fan-out within a session but not across sessions.

**Problem 5 — E2E mode disables rate limiting entirely**: `MNM_E2E_SEED=true` disables rate limiting for ALL requests, not just for test users. If this env var were accidentally set in production, rate limiting is silently off.

**Problem 6 — Fixed-window counter race (Redis incr + expire)**: The Redis implementation uses `INCR` followed by `EXPIRE` — a classic race condition. If the server crashes between `INCR` (count=1) and `EXPIRE`, the key has no TTL and the counter never resets. Mitigation: use a Lua script or `SET NX PX` atomic operation.

## Impact

- Multi-instance deployments without Redis are effectively unprotected.
- Expensive AI endpoints can be hammered at 500/min per actor/company combination.
- A Redis failure silently degrades to per-instance limits without alerting.

## Recommendation

1. Use a single Redis Lua script for atomic increment-and-expire.
2. Add a per-IP rate limiter (`ip`-keyed) as a first line of defense before auth.
3. Add a separate, stricter limit for LLM/SSE endpoints (e.g. 20 req/min).
4. Scope `MNM_E2E_SEED` to a test-specific actor/token rather than globally disabling rate limiting.
5. Alert (don't just warn) when falling back from Redis to in-memory.
6. The `perCompanyKeyGenerator` helper exists but is **not wired** into the app. Consider adding a per-company ceiling alongside the per-actor one.
