## Description

Several mutation routes pass `req.body` (or a derivative spread of it) directly to the service layer without whitelisting accepted fields. The `validate()` middleware strips unknown fields only when the schema uses `.strict()`. Most schemas imported from `@mnm/shared` use Zod default mode which silently **strips** unknown fields at the middleware level — however the `validate` middleware in `server/src/middleware/validate.ts` reassigns `req.body = result.data`, so the service receives only schema-approved fields.

The problem is that several routes **bypass `validate()`** and pass raw `req.body` directly:

| Route | File:Line | Risk |
|---|---|---|
| `POST /goals` | goals.ts:34 — `svc.create(companyId, req.body)` | validate() is present but check service type |
| `PATCH /goals/:id` | goals.ts:67 — `svc.update(id, req.body)` | validate() used, but service type is `Partial<goals.$inferInsert>` — all DB columns |
| `PATCH /companies/:companyId` | companies.ts:180 — `svc.update(companyId, req.body)` | validate() present |
| `PATCH /projects/:id` | projects.ts:154 — `svc.update(id, req.body)` | validate() present |
| `PATCH /agents/:id/permissions` | agents.ts:963 — `svc.updatePermissions(id, req.body)` | validate() present |

The critical case: `goalService.update()` (services/goals.ts:23) calls `db.update(goals).set({ ...data, updatedAt: new Date() })` where `data` is typed as `Partial<typeof goals.$inferInsert>`, meaning ALL table columns are technically valid. If Zod's `updateGoalSchema` is not `.strict()`, extra fields such as `id`, `companyId`, `createdAt` could pass through.

Similarly `svc.update(id, req.body)` in projects and companies delegates to service methods typed as `Partial<T>` over the full DB schema.

**Confirmed non-strict**: Without seeing `updateGoalSchema` source, the Zod default strips unknown keys from parsed output — BUT the `validate` middleware assigns `req.body = result.data` so the path is safe IF all mutation routes use `validate()`. The vulnerability window is routes that do NOT use `validate()`:

- `issues.ts:616` — `const { comment: commentBody, hiddenAt: hiddenAtRaw, ...updateFields } = req.body` — `updateFields` is then passed directly to `svc.update(id, updateFields)` after Zod validates via `validate(updateIssueSchema)` at the route level. ✓ Safe here.
- `agents.ts:1325` — `svc.createApiKey(id, req.body.name)` — only `.name` extracted. ✓ Safe.
- `a2a.ts:308` — `permSvc.createRule(companyId, req.body)` — `validate(createA2APermissionRuleSchema)` is chained. ✓ Safe.
- `a2a.ts:579` — `mcpSvc.updateConnector(companyId, connectorId, req.body)` — `validate(updateMcpConnectorSchema)` is chained. ✓ Safe.

**Residual risk**: Any schema that is NOT strict still silently strips unknown fields at parse time, but the current `validate` middleware will already return `result.data`. The risk remains if a developer adds a new mutation route without `validate()` (low guard).

More immediately: `goals.ts:34` uses `validate(createGoalSchema)` and then `svc.create(companyId, req.body)`. After `validate()`, `req.body` is `result.data`, so it is the parsed output — BUT the goal service's `create` method takes `Omit<goals.$inferInsert, "companyId">` which includes `id`. If `createGoalSchema` allows an optional `id` field, a caller could supply their own UUID.

## Impact

- Potential field injection to supply internal-only fields (id, companyId, createdAt, internal flags).
- In schemas not typed strictly, future column additions may auto-become writable from the API.

## Reproduction

Craft a PATCH body with `id` or `companyId` if those fields are not explicitly excluded by the schema.

## Recommendation

1. Audit every `@mnm/shared` schema (createGoalSchema, updateGoalSchema, etc.) to ensure all mutable schemas use `.strip()` or better `.strict()` and explicitly exclude server-only fields like `id`, `companyId`, `createdAt`, `updatedAt`.
2. Enforce a lint/type rule: no route may call a service `create/update` method with raw `req.body` without first passing through `validate()`.
3. Consider using `z.object({...}).omit({ id: true, companyId: true, createdAt: true })` pattern on all update schemas.
