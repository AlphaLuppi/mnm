## Description

`GET /api/health` is mounted inside the `/api` router (`app.ts:265-274`) but does **not** require authentication. In `local_trusted` mode this is intentional, but in `authenticated` mode the endpoint returns:

```json
{
  "status": "ok",
  "db": {
    "connected": true,
    "latencyMs": 1.23,
    "version": "16.1"
  },
  "rls": {
    "tablesProtected": 48
  },
  "redis": {
    "configured": true,
    "connected": true,
    "latencyMs": 0.5
  },
  "deploymentMode": "authenticated",
  "deploymentExposure": "private",
  "authReady": true,
  "bootstrapStatus": "ready",
  "hasCompany": true,
  "features": {
    "companyDeletionEnabled": false
  }
}
```

This leaks:
- **PostgreSQL version string** — attackers can target known CVEs for that PG version.
- **Redis presence and latency** — confirms internal topology.
- **Table count with RLS** — confirms database schema size, useful for enumeration.
- **Deployment topology** (mode, exposure, company existence) — useful for targeted attacks.
- **`bootstrapStatus: "bootstrap_pending"`** — signals that the instance has no admin user and may be in a one-time-claim state (attackers could attempt to claim it).

The `bootstrapStatus` finding is particularly sensitive: an internet-facing instance advertising `bootstrap_pending` is an invitation for a race attack.

## Impact

- Zero-auth information disclosure about server infrastructure.
- An attacker can confirm the target runs PostgreSQL 16.x and look up matching CVEs.
- `bootstrap_pending` state is publicly visible.

## Reproduction

```bash
curl http://TARGET/api/health
```

## Recommendation

1. Return a minimal public response: `{ "status": "ok" }` without auth.
2. Gated by auth: return full details only for `isInstanceAdmin` actors.
3. Or: suppress `db.version`, `rls`, `redis` keys in non-local deployments.
4. At minimum, hide `bootstrapStatus: "bootstrap_pending"` from unauthenticated callers — replace with `{ "bootstrapRequired": true }` and redirect to setup page.
