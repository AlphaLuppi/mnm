## Description

The widget generation endpoint (`POST /companies/:companyId/user-widgets/generate`) uses a configurable LLM endpoint from environment variable `MNM_LLM_SUMMARY_ENDPOINT`:

```typescript
// user-widgets.ts:196-220
const llmEndpoint = process.env.MNM_LLM_SUMMARY_ENDPOINT;
...
if (llmEndpoint && llmApiKey) {
  const response = await fetch(llmEndpoint, {  // No URL validation
    method: "POST",
    ...
  });
}
```

While this is an operator-configured value (not user-supplied directly), it represents a class of SSRF via misconfiguration: if an attacker can influence environment variables (via `.env` file injection, container escape, or CI/CD compromise), they can redirect LLM traffic to an internal endpoint.

More immediately, the `repo_url` field in the plugin import endpoint (`POST /governed-workflows/import-plugin`) is user-supplied and forwarded to `buildSourceProvider()` which resolves a GitProvider — depending on implementation, this could also fetch from attacker-controlled URLs.

Additionally, the Jira import (`SEC-T5-002`) is a confirmed SSRF path.

This finding documents the `MNM_LLM_SUMMARY_ENDPOINT` pattern specifically because it:
1. Has no URL validation (protocol, hostname).
2. Sends the company's widget prompt system context to the external endpoint, potentially leaking internal business data.
3. Receives and parses the response as JSON with no content-length limit beyond the 60-second timeout.

## Impact

- Internal data leakage to attacker-controlled LLM endpoint via misconfiguration.
- Potential SSRF in container environments.

## Recommendation

1. Validate `MNM_LLM_SUMMARY_ENDPOINT` at startup: must be `https://` only, must resolve to a public IP.
2. Log a startup warning if the endpoint hostname resolves to a private IP.
3. Consider schema-validating the response from the LLM endpoint before using it.
