## Description

The fallback key generator in `createRateLimiter` uses `req.ip`:

```typescript
keyGenerator = (req: Request) => req.ip ?? "unknown"
```

The app-level key generator uses `req.ip` for unauthenticated actors:

```typescript
: req.ip ?? "unknown"
```

Express sets `req.ip` from `X-Forwarded-For` **only when `app.set('trust proxy', ...)` is configured**. There is no `app.set('trust proxy')` call anywhere in `server/src/app.ts` or `server/src/index.ts`.

**Without trust proxy**, `req.ip` is always the direct TCP connection IP (the actual socket peer). This has two opposite failure modes:

1. **Behind a load balancer (reverse proxy)**: Every request from the load balancer has the same `req.ip` (the proxy's IP). All traffic is bucketed under one rate limit key, so one rogue client can exhaust the 500 req/min budget for all clients.

2. **Directly exposed**: The rate limiter key correctly uses the true client IP, but any attacker who can control the socket (i.e., from a different IP) is not affected by other IPs' limits — which is correct behavior here.

The `require-permission` middleware also logs `req.ip`:
```typescript
// require-permission.ts:33
ipAddress: req.ip ?? req.socket?.remoteAddress ?? null,
```
In a reverse-proxy deployment, all permission-violation audit logs will show the load balancer IP rather than the client IP, undermining forensics.

Additionally, `private-hostname-guard.ts` reads `X-Forwarded-Host` without restriction, potentially allowing hostname bypass via header injection if a permissive proxy forwards arbitrary client headers.

## Impact

- In load-balanced production deployments, IP-based rate limiting collapses to a single bucket per proxy — effectively no per-client IP throttling.
- Audit trail for permission violations logs incorrect IP.

## Reproduction

```bash
# From behind the same proxy IP:
for i in $(seq 1 600); do
  curl -s http://PROXY_IP/api/companies/X/goals -o /dev/null &
done
# All 600 requests share the same req.ip bucket
```

## Recommendation

1. Configure trust proxy explicitly based on deployment topology:
```typescript
// In createApp, before any middleware:
if (opts.deploymentMode === "authenticated" && behindProxy) {
  app.set("trust proxy", 1); // trust one hop
}
```
2. Document the trust proxy setting in deployment docs.
3. In `private-hostname-guard.ts`, validate that `X-Forwarded-Host` is only trusted when `trust proxy` is set.
