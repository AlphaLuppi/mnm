## Description

The `validate()` middleware only validates `req.body`:

```typescript
// middleware/validate.ts:4-13
export function validate(schema: ZodSchema) {
  return (req: Request, _res: Response, next: NextFunction) => {
    const result = schema.safeParse(req.body);  // body only
    if (!result.success) { next(result.error); return; }
    req.body = result.data;
    next();
  };
}
```

Query parameters (`req.query`) and path parameters (`req.params`) are universally accessed by casting: `req.query.limit as string`, `req.params.companyId as string`, with no Zod validation applied.

Specific examples:

**Query params not validated:**
- `GET /companies/:companyId/documents` — `req.query.status as string` — arbitrary string passed to `docSvc.list()` as a filter with no enum validation.
- `GET /companies/:companyId/costs/*` — `req.query.from`, `req.query.to` passed as `new Date(query.from as string)` — `new Date("__proto__")` is `Invalid Date` but doesn't throw; passed to SQL query may produce unexpected behavior.
- Multiple `?limit=` / `?offset=` — see SEC-T5-006.
- `GET /governed-workflows/:name/files?ref=` — git ref from user with no length limit or character validation.

**Path params not validated:**
- `req.params.companyId as string` — UUID format is validated in `assertCompanyMembership` for company-scoped routes but NOT for routes outside the `api.use("/companies/:companyId", ...)` middleware chain.
- `req.params.adapterType` in `llms.ts:68` — arbitrary string; handled correctly here (find then 404) but no Zod constraint.

**The `ref` parameter for git operations** is particularly sensitive. The `governedWorkflowFilesRoutes` GET endpoint passes `req.query.ref` directly to git provider operations without length limits or character restrictions:
```typescript
// governed-workflows-files.ts:124
const queryRef = req.query.ref as string | undefined;
const ref = queryRef ?? def?.latestGitTag ?? "main";
// passed directly to gitProvider.fetchTree({ ref, ... })
```
A very long `ref` value or a ref with special characters (`;`, `|`, `` ` ``) could be problematic depending on the underlying git provider implementation.

## Impact

- Unexpected behavior from unvalidated status/date filters.
- Potential injection via git ref parameter.
- Inconsistent error messages that may leak schema information.

## Recommendation

1. Extend `validate()` or create `validateQuery(schema)` and `validateParams(schema)` middleware helpers.
2. At minimum, validate known enum values: `status` should be `z.enum(["processing","ready","error"])`, `ref` should be `z.string().max(200).regex(/^[A-Za-z0-9/_.-]+$/)`.
3. Validate `from`/`to` dates with Zod `z.coerce.date()`.
