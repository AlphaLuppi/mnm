## Description

The `errorHandler` middleware in `error-handler.ts` handles three error classes:

1. **HttpError** (from `errors.ts`): returns `{ error: err.message, details: err.details }` — message is developer-written, acceptable.
2. **ZodError**: returns `{ error: "Validation error", details: err.errors }` — Zod error details include field paths and expected types. This is intentionally helpful for API consumers but leaks schema structure.
3. **All other errors** (including database errors from Drizzle/pg): returns `{ error: "Internal server error" }` — the message is safely opaque. ✓

The 500-path is correctly handled. However:

**HttpError `details` field**: Several places construct `HttpError` with DB-derived `details`:
```typescript
// errors.ts conflict()
export function conflict(message: string, details?: unknown) {
  return new HttpError(409, message, details);
}
```
If any service passes a PostgreSQL constraint violation object as `details`, it would be returned to the client. An audit of services passing `details` to `conflict()/unprocessable()` is needed.

**ZodError details exposure**: The full Zod error object is returned including field paths:
```typescript
res.status(400).json({ error: "Validation error", details: err.errors });
```
While useful for development, in production this reveals:
- All schema field names
- Expected types per field
- Enum values

For internal-only APIs this is acceptable. For public-facing APIs (invite accept, MCP auth) it may over-disclose.

**Stack trace in error context**: `attachErrorContext` stores `err.stack` in `(res as any).__errorContext`. This is not sent to the client — it's for internal use by a logger or APM. No issue.

**Timing differences**: No timing oracle was observed in authentication paths. The `actorMiddleware` always calls `next()` regardless of auth outcome, adding no conditional delays.

## Impact

- Low: Zod validation errors reveal field names and expected types to API consumers.
- Low: `details` in HttpError could theoretically include DB constraint names if services pass them through.

## Recommendation

1. In production (`NODE_ENV=production`), strip Zod error `details` to just the field paths: `details: err.errors.map(e => ({ path: e.path, code: e.code }))`.
2. Audit all `conflict()` / `unprocessable()` callsites to ensure no DB error is passed as `details`.
3. Document that `HttpError.details` must never contain raw database error objects.
