## Description

`express.raw({ type: "application/json", limit: "10mb" })` is applied globally to every route on the server, including low-cost read-only endpoints (GET /companies/:companyId/goals, GET /api/auth/get-session, etc.). Any authenticated or unauthenticated actor can POST a 10 MB JSON body to any route, consuming significant CPU for JSON parsing even when the route discards the body.

Furthermore, `express.urlencoded` is only applied on individual MCP OAuth sub-routes and not globally, so URL-encoded bodies sent to JSON routes are silently ignored rather than rejected — this is a quirk that could mask future bugs.

There is no secondary per-route size limit on any individual route. The body is always read in full before any auth middleware runs.

## Impact

- Sustained 10 MB POST flood to any endpoint (including public `/api/health`) forces the server to read, buffer, and decode 10 MB per request.
- With the default 500 req/min rate limiter and no per-IP cap on body size, a single actor can push ~83 MB/s through the JSON decoder.
- No cost-based rate limiting; LLM-adjacent endpoints like `POST /ai/chat` are under the same ceiling.

## Reproduction

```bash
# 9.9 MB body to a GET-only endpoint (Express does not block body on GET)
python3 -c "import sys; sys.stdout.buffer.write(b'{\"x\":' + b'1' * 9_900_000 + b'}')" | \
  curl -s -X POST http://localhost:3100/api/companies/COMPANY_ID/goals \
    -H 'Content-Type: application/json' --data-binary @-
```

## Recommendation

1. Reduce global JSON limit to 1 MB (or 512 KB) — the vast majority of API payloads are well under 100 KB.
2. Apply an explicit larger limit only on routes that need it (e.g. document summarize which sends `extractedText`).
3. Add a separate per-IP rate limiter in front of the body-parsing step so large-body attacks are throttled before CPU is spent.
