## Description

Both `docker-compose.yml` (production) and `docker-compose.dokploy.yml` bind-mount the host Docker socket directly into the server container:

```yaml
volumes:
  - /var/run/docker.sock:/var/run/docker.sock
```

The `entrypoint.sh` then adds the `mnm` user to the Docker group so it can use the socket:

```sh
groupadd -g "$DOCKER_GID" docker 2>/dev/null || true
usermod -aG docker mnm 2>/dev/null || true
```

The container process (running as non-root `mnm` user) therefore has full unrestricted access to the host Docker daemon. This is architecturally equivalent to root-on-host: an attacker who compromises the `mnm` process can create privileged containers, escape to the host filesystem, mount `/` from the host, and achieve full host takeover.

## Impact

- **Container escape to host root** — any code execution vulnerability in the server (e.g., SSRF, deserialization, RCE in Express routes, shell injection in drift-analyzer) immediately grants full host control.
- **Lateral movement** — attacker can start new containers with access to all host volumes, other services, credentials stored on host.
- **Supply chain leverage** — if any npm package in the dependency tree is compromised, the blast radius is the entire Docker host rather than the container.

Severity: **CRITICAL**. This is a well-documented Docker escape vector (DockStation, HackTricks, OWASP Docker Security).

## Reproduction

1. Obtain code execution inside the `server` container (e.g., via one of the shell injection paths).
2. Connect to `/var/run/docker.sock` using `docker` CLI (pre-installed in the container).
3. Run `docker run -v /:/host -it ubuntu chroot /host` to get a root shell on the Docker host.

## Recommendation

1. **Preferred**: Replace direct socket mount with a **Docker socket proxy** (e.g., `tecnativa/docker-socket-proxy`) that allowlists only the specific API calls needed (container create, start, stop, exec for sandbox management). Mount the proxy socket instead.
2. **Alternative**: Evaluate whether Docker-in-Docker (using the `DOCKER_HOST` env var pointing to a scoped proxy) satisfies operational needs.
3. If the socket must stay, restrict it to a named Docker context with reduced surface, and apply `seccomp`/`AppArmor` profiles to the server container to limit syscalls.
4. At minimum, document this as an intentional architectural decision with explicit threat model acknowledgment.
