## Description

None of the docker-compose files apply Linux security modules or privilege escalation prevention:

- No `security_opt: ["no-new-privileges:true"]` on any service.
- No `security_opt: ["seccomp=..."]` profile.
- No `security_opt: ["apparmor=..."]` profile.
- No `cap_drop: ["ALL"]` with selective `cap_add`.

Without `no-new-privileges`, a process inside the container could use `setuid` binaries to escalate to root even after `gosu` drops to `mnm`. Without a seccomp profile, all ~300+ Linux syscalls are available to the container, many of which are not needed by a Node.js web server.

The default Docker seccomp profile blocks ~44 syscalls, but the `docker-compose.yml` does not reference it explicitly, meaning behavior depends on Docker daemon default configuration, which may be disabled on some hosts.

## Impact

- A compromised `mnm` process could use `setuid` binaries to escalate to root within the container.
- Without syscall filtering, kernel exploits (e.g., `dirty pipe`, future N-days) are more accessible to a compromised container process.
- Risk is lower in practice due to `gosu` privilege drop, but defense-in-depth is absent.

## Reproduction

1. Inside the running container: `find / -perm -4000 2>/dev/null` to find setuid binaries.
2. Check if `no-new-privileges` is enforced: `docker inspect <container> | grep -i NoNewPrivileges`.

## Recommendation

Add to all production compose services:

```yaml
security_opt:
  - no-new-privileges:true
cap_drop:
  - ALL
cap_add:
  - NET_BIND_SERVICE  # only if binding to port < 1024
```

For the `db` (PostgreSQL) service, PostgreSQL needs some capabilities — test with `cap_drop: ALL` and selectively re-add if startup fails.
