## Description

There is an inconsistency between the default host binding in the Dockerfile and the server config:

**Dockerfile** (line 73):
```dockerfile
ENV NODE_ENV=production \
  HOME=/mnm \
  HOST=0.0.0.0 \
  PORT=3100 \
```

**Server config** (server/src/config.ts:209):
```typescript
host: process.env.HOST ?? fileConfig?.server.host ?? "127.0.0.1",
```

In the Docker production environment, `HOST=0.0.0.0` is set, so the server binds to all interfaces. This is correct for a containerized deployment where the host binding must be `0.0.0.0` for Docker port mapping to work.

However, the default fallback in config (`127.0.0.1`) is only used when neither `HOST` env var nor file config provides a value. The problem is:

1. `docker-compose.quickstart.yml` also sets `HOST: "0.0.0.0"` explicitly.
2. The dev config default (`127.0.0.1`) is safe, but the production Dockerfile ENV hardcodes `0.0.0.0` globally — including for builds that might be used in non-expected network topologies.
3. `dev:docker:up` / `bun run local` don't expose this ENV directly, so dev server picks up `127.0.0.1` — but the container build always has `0.0.0.0` baked in.

In the dokploy deployment, the server is behind Traefik (`expose:` not `ports:`), so `0.0.0.0` binding is effectively scoped to the Docker network. But for standalone `docker-compose.quickstart.yml` usage without a reverse proxy, binding to `0.0.0.0` means the server is reachable on all host interfaces.

## Impact

- If a user runs the quickstart container on a host with a public IP and no firewall, the MnM server is exposed on `0.0.0.0:3100` — reachable from the internet.
- `MNM_DEPLOYMENT_EXPOSURE: "private"` and `MNM_ALLOWED_HOSTNAMES` provide application-level guards but do not replace network-level binding restriction.
- No `UFW`/`iptables` hint in the documentation means a new deployer may not know to restrict this.

## Reproduction

1. Run `docker compose -f docker-compose.quickstart.yml up` on a cloud VM.
2. Check what's listening: `ss -tlnp | grep 3100` or `netstat -tlnp | grep 3100`.
3. If no firewall is in place, the server is reachable publicly.

## Recommendation

1. Document clearly in the quickstart README that a firewall (e.g., security group, `ufw allow from ...`) must restrict port 3100 to trusted sources.
2. Consider changing the quickstart compose to bind to `127.0.0.1` by default and document how to change for reverse-proxy use:
   ```yaml
   ports:
     - "127.0.0.1:${MNM_PORT:-3100}:3100"
   ```
3. The `private-hostname-guard` middleware provides some protection but is application-layer only.
