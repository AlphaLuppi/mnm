## Description

The repository has a `.github/` directory but contains **no GitHub Actions workflow files** — only issue templates and a PR template:

```
.github/ISSUE_TEMPLATE/bug_report.md
.github/ISSUE_TEMPLATE/config.yml
.github/ISSUE_TEMPLATE/feature_request.md
.github/ISSUE_TEMPLATE/question.md
.github/pull_request_template.md
```

The `package.json` includes a `release` script (`./scripts/release.sh`) and `changeset` tooling. The repo has a `releases/v0.2.7.md` file suggesting releases have occurred, but there is no automated CI pipeline to:

1. Build and sign Docker images.
2. Verify dependency integrity (e.g., `bun.lock` hash check).
3. Run security scans (Trivy, Snyk, npm audit).
4. Enforce branch protection / required status checks.
5. Attest release artifacts (SLSA provenance).

Without a CI/CD pipeline, the security posture of releases is entirely manual and unverified. The `./scripts/release.sh` script is used to publish, but we cannot inspect whether it signs artifacts, pushes to a registry with provenance, or validates tests pass first.

Additionally, `bun run release.sh` is a shell script that may be run locally — meaning a developer's compromised machine could push a release.

## Impact

- No automated security scanning means vulnerabilities in dependencies may be shipped undetected.
- No image signing means users cannot verify that a pulled Docker image is genuine.
- No SLSA provenance means the supply chain cannot be verified.
- Manual release process is susceptible to human error and local machine compromise.

## Reproduction

- Check `.github/workflows/` — directory is empty (no workflow files).
- `cat scripts/release.sh` to verify whether it signs artifacts.

## Recommendation

1. Add a CI pipeline with at minimum:
   - `bun run typecheck && bun run test:run` on all PRs.
   - `docker build` on all PRs.
   - `trivy image` or `docker scout` on built images.
   - `bun audit` / `npm audit` for dependency vulnerabilities.
2. Add a release workflow that:
   - Builds Docker images and pushes with SHA-pinned tags.
   - Signs images with `cosign` (keyless signing via OIDC).
   - Generates SBOM and attaches to release.
3. Enforce branch protection on `main`: require PR, require status checks.
4. Pin any third-party actions to SHA commits (not mutable tags) when workflows are added.
