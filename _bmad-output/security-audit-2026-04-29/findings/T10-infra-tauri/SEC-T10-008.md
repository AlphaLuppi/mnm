## Description

None of the production or deployment docker-compose files define resource limits for any container:

- No `deploy.resources.limits` (for Docker Swarm / Compose v3)
- No `mem_limit` / `cpus` (for Compose v2 syntax)
- No `ulimits`

The containers affected: `server`, `db` (postgres), `redis`.

Redis has a `maxmemory` setting (`256mb`) at the application level via CLI flags, which provides partial protection for Redis. However, the server container and PostgreSQL have no OS-level constraints.

An attacker who can trigger expensive operations (large trace ingestion, concurrent heartbeat runs, drift analysis loops, WebSocket floods) can cause OOM or CPU exhaustion that takes down the container and potentially the host if containers share host resources without namespace limits.

The `shm_size: 256mb` on the db service only affects shared memory, not total memory.

## Impact

- Unrestricted memory consumption in the `server` container can cause OOM kills that crash all containers on the host.
- A single malicious company/user with access to the API can trigger expensive LLM calls or trace processing in a tight loop.
- No CPU limits means a CPU-bound attack (e.g., expensive regex, JSON parsing of large payloads) can starve other containers.

## Reproduction

1. Authenticate as a valid user.
2. Submit a large trace payload or trigger multiple concurrent heartbeat runs.
3. Monitor container memory: `docker stats`.

## Recommendation

Add resource limits to all production compose configurations:

```yaml
services:
  server:
    deploy:
      resources:
        limits:
          cpus: "2.0"
          memory: 2G
        reservations:
          memory: 512M
  db:
    deploy:
      resources:
        limits:
          memory: 1G
  redis:
    deploy:
      resources:
        limits:
          memory: 512M
```

Also add `ulimits` to prevent process/file descriptor exhaustion:

```yaml
ulimits:
  nofile:
    soft: 65536
    hard: 65536
```
