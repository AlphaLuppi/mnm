## Description

The e2e test fixture file commits a hardcoded password for all test users:

```typescript
export const TEST_PASSWORD = "E2eTestPass!2026";
```

This password is used for all 5 test user accounts (admin, manager, contributor, viewer, atelierAdmin across two companies). The `.gitignore` excludes `e2e/.auth/` (auth state files) correctly, but the source fixture file containing the password itself is committed.

Additionally, the auth storage state files (`e2e/.auth/*.json`) ARE present in the working tree:
- `/e2e/.auth/adminStorageState.json`
- `/e2e/.auth/storageState.json`
- etc.

These files contain `{"cookies":[],"origins":[]}` (empty), so they do not contain active session tokens. However, they are present in the working tree despite `.gitignore` listing `e2e/.auth/`. This suggests they were committed before the gitignore rule was added, or were generated locally and not cleaned up.

The key risk is `seed-data.ts` containing `TEST_PASSWORD` — if this password is reused on production or staging deployments that run with `MNM_E2E_SEED=true`, it gives any user who knows the password (i.e., anyone with repo access) admin access to those systems.

## Impact

- Any attacker with repository read access knows the admin test credential.
- If `MNM_E2E_SEED=true` is accidentally set on a staging/production deployment, the seeded admin account (`admin@novatech.test` / `E2eTestPass!2026`) becomes a backdoor admin account.
- The password policy is inconsistent — while the `MNM_E2E_SEED` guard exists, the seed data also includes real email-format addresses (`admin@novatech.test`, `manager@novatech.test`) that users might accidentally activate on real tenants.

## Reproduction

1. Read `e2e/fixtures/seed-data.ts` line 110.
2. Find any deployment where `MNM_E2E_SEED=true`.
3. Login with `admin@novatech.test` / `E2eTestPass!2026`.

## Recommendation

1. Move `TEST_PASSWORD` to an environment variable (`E2E_TEST_PASSWORD`) loaded from `.env.test` (gitignored):
   ```typescript
   export const TEST_PASSWORD = process.env.E2E_TEST_PASSWORD ?? "E2eTestPass!2026";
   ```
   With a CI secret for the real value.
2. Add a validation in the e2e-seed endpoint to reject passwords matching known defaults when not in a local-dev context.
3. Verify `e2e/.auth/*.json` files are not tracked by git: `git ls-files e2e/.auth/` should return empty.
4. Ensure `MNM_E2E_SEED` is explicitly set to `false` in all production docker-compose configurations (currently done in `docker-compose.dokploy.yml` — verify all production paths).
